# 需求澄清与架构设计：运营 Agent（v0.2 大版本）

> 状态：草案 v1，待用户 review。基于 src/agent/runner（旧内部 Agent）整合取代、先出设计再写码。
> 纪律：边界与验收由用户拍板；本文件只描述方案，不含实现代码。

## 1. 复述诉求（对齐用，v2 收敛后）

用户要的"Agent运营"——沙箱环境是现有聚合中转平台，重新造一个 Agent：

- 给**运营人员**用的运营 Agent，**整合取代**现有内部运维 Agent（src/agent/runner）。
- **关键收敛（用户拍板）**：真隔离（容器/进程级代码执行沙箱）在零依赖下做不到，故**不做独立代码执行沙箱**。
  改为——**围绕中转平台本身的规则造 Agent**：Agent 的工具 = 平台已有能力（model 路由 / KB / key 管理 / 流控 / 事件 / 计量），
  它的活动边界天然就是"平台规则"本身（受计量/归因/熔断/鉴权保护）。不需要通用代码执行沙箱。
- 工具集 = 平台内置工具 + 可注册**外部 HTTP 工具**（受平台 key/timeout/出口约束）。
- 越界动作（外部 HTTP 写操作、平台变更类）**需人工审批**，异步模式（Agent 先回"已提交审批"，批后回填）。
- 本大版本**一次性把"平台内容规则 Agent"做完整**，不先做阉割 MVP。
- 审批模式：**异步**（已拍板）。

## 2. 5Why：真实目标

1. 为什么要"运营 Agent"？→ 让运营人员用自然语言驱动平台运维/运营动作，降低人工操作成本。
2. 为什么用"沙箱=中转平台"？→ Agent 的工具应是平台已有能力（model 路由/key/流控/KB/事件），复用且天然受计量/归因/熔断保护（旧 runner 已验证"网关调自己"闭环的价值）。
3. 为什么"任意工具含代码执行"？→ 运营场景多变，固定工具不够，需要可注册 HTTP 工具和可执行脚本做临时数据/自动化任务。
4. 为什么"需审批"？→ 代码执行 + 任意 HTTP 是重大攻击面与误操作面，越界动作必须人工确认（fail-closed 安全取向）。
5. 真实目标 → **一个受管、可审计、可审批的运营 Agent 运行时，工具集可扩展，危险动作不自动执行。**

## 3. 现有资产复用（不重复造）

- KbStore（src/kb/store.ts）：检索/文档 CRUD，Agent 知识源直接复用。
- /v1/chat/completions + /v1/kb/{id}/ask：LLM 与 KB 问答入口已存在。
- AgentRunner 旧范式"网关调自己被计量保护"——新运行时沿用。
- store.logEvent：审批/工具调用审计落痕复用。
- 面板 Agent 区、key/流控/事件——UI 扩展点。

## 4. 功能项（F）与非功能项（N）、约束（C）

### F1 运营 Agent 运行时
- 取代 src/agent/runner；多轮会话（session），每轮：组装上下文→调 LLM（带 tool_calls）→执行工具→回填结果→再调 LLM→产出最终回复/动作建议。
- 沿用"走本网关 /v1/chat/completions"入口（自带计量/归因/熔断）。

### F2 工具系统
- F2.1 平台内置工具：kb_search / kb_ask / list_keys(masked) / flow_status / list_events / model_list。
- F2.2 外部 HTTP 工具：可配置注册 {name, method, url, headers, schema}，受平台 key/timeout 约束。
- F2.3 代码执行工具：执行 JS/Python 片段（见 N3 沙箱）。

### F3 审批流
- 越界动作（外部 HTTP 写操作、代码执行、平台变更类）生成 pending 审批单，写入 store 事件；
- 运营人员在面板/API 审批（approve/reject），Agent 拿到批准后才执行；
- 超时未批自动 reject（fail-closed）。

### F4 持久化与会话
- Agent 会话、工具注册、审批单、执行记录持久化（复用 SqliteStore / 新增 agent 表）。

### F5 面板 UI
- 运营 Agent 对话页、工具注册管理、审批队列、执行历史。

### N1 安全（最高优先级）
- 主路径（鉴权/路由/透传）完全不碰 Agent；Agent 故障绝不影响网关转发（沿用旧不变量）。
- 所有 Agent LLM 调用带 client_kind=agent 指纹，可识别可归因。
- 危险动作 fail-closed（默认不执行，需审批）。

### N2 边界即平台规则（核心安全范式，替代代码执行沙箱）
- 不做通用代码执行沙箱（零依赖下真隔离不可行，用户已拍板）。
- Agent 的所有能力都通过"平台工具"暴露，工具本身受网关既有护栏保护：
  鉴权（timeSafeEqual + 锁）、日志脱敏、计量/归因、熔断/限流、出口白名单。
- 新增的外部 HTTP 工具：受平台 key 注入、timeout、以及**出口名单（C8 同款闸门）**约束，不裸奔出网。
- 危险动作（外部写、平台变更）走审批流，fail-closed。


- 每次工具调用、审批、执行结果写入审计事件；面板可回溯。

### C1 零运行时依赖
- 新增代码只用 node 内置；若选 L3 沙箱需明确偏离并用户同意。

### C2 整合取代
- 旧 src/agent/runner 标记 deprecated 并最终移除；新运行时统一接口。

## 5. 边界（不做什么）

- 不做 C 端多租户 Agent 产品（本版只运营人员）。
- **不做通用代码执行沙箱 / 任意脚本执行**（用户已拍板，零依赖下真隔离不可行）。
- 不做 Agent 自主训练/微调（只调已有 model）。
- 不做无审批的自动平台变更（fail-closed）。
- 不引入运行时依赖（外部 HTTP 工具用 node 内置 fetch；无需额外包）。

（每条可检验）

- AC1：运营人员通过 API/面板发起多轮对话，Agent 能连续调用 ≥2 个平台工具并产出正确最终答复。
- AC2：注册一个外部 HTTP 工具（GET 类），Agent 能调用并解析结果；写类外部工具触发审批单。
- AC3：代码执行工具在 L1 下能跑纯计算并返回结果；死循环被 timeout 终止（不拖垮网关）。
- AC4：越界动作生成 pending 审批单；超时未批自动 reject，Agent 不执行。
- AC5：Agent 故障（LLM 不可达）时网关转发主路径 0 影响（压测/注入验证）。
- AC6：所有 Agent LLM 调用在计量里可识别 client_kind=agent。
- AC7：旧 src/agent/runner 已 deprecated 且新运行时覆盖其原有 view/trigger 能力。
- AC8：CI（Node 22）全绿，含新增测试。

## 7. 已拍板 / 待定

- 已拍板：沙箱=平台规则（不做代码执行沙箱）；审批=异步；本版一次性做完整平台规则 Agent。
- 已拍板（用户确认）：外部 HTTP 工具"需审批"口径 = **写操作（POST/PUT/DELETE/PATCH）需审，GET 免审，不叠加域名白名单**（用户回复"1"）。
- 已拍板（整合取代初衷）：旧 src/agent/runner 本版结尾**直接移除**（非 deprecated 过渡），新运行时完全覆盖其 view/trigger/决策历史能力。
- 已消解：不做阉割 MVP，本版完整交付。

## 8. 实施纪律（写码阶段）

- 先 commit 本设计文档 + git 回滚点，再进入写码；写码阶段调度 subagent 并行实现 A/B/C/D 阶段模块。
- 每阶段结束跑 typecheck + build + test，CI（Node 22）作为最终门禁。
- 不动主路径（鉴权/路由/透传）安全不变量；Agent 故障 0 影响网关转发。
- 零运行时依赖铁律：外部 HTTP 工具仅用 node 内置 fetch。
