## 3. 今天做完的（审计后累计 13 个提交，全部上线）

### 3.1 速度问题的根因：DNS 污染 —— `e6b533b`

真凶是本机解析器上游 **`114.114.114.114` 对 `api.agnes-ai.cn` 回了假 IP**：

```
@114.114.114.114   183.131.87.105   ← 假！TCP 连得上，但永不回数据
@223.5.5.5/119.29/8.8.8.8   118.180.26.76   ← 真的
@127.0.0.53        183.131.87.105   ← 本机 stub 跟着错
```

修法（新增两个模块）：`src/upstream/dns.ts`（c-ares 直连可信 DNS，不走系统解析器）+ `src/upstream/http2.ts`
（零依赖 HTTP/2，伪装成 fetch 返回标准 `Response`，管线一行没改；支持 `connectIp` 按 IP 建连、SNI 仍用真域名）；
首字节闸门 60→90s。**效果**：客户首字节均值 27.5s → 5.9s，成功率恢复 100%。

⚠️ 教训：h2 第一版上线把服务打挂了（没先绕开污染 DNS）。**传输层改造必须和名字解析一起验。**

### 09-16 00:xx 双线路对冲上线（保"任务完成率"）

**做了什么**：新增 `server.hedgeDelayMs`（默认 0；本部署 `relay-net.yaml` = 20000）。同一模型

**实测（关键，别删）**：

| 阈值 | 结果 |
|---|---|
| 8 秒 | 9 个 128KB 请求**全部触发对冲、备线路 0 次赢** —— 备线路 agnes 国际**稳定更慢**，8 秒只是白白翻倍调用 |
| 20 秒 | 8.6/8.9 秒的正常请求**不触发**；一个 36.9 秒的长尾请求**对冲命中**，备线路在 TTFB **16.9 秒**就出了内容 |

备线路若长期更慢，可把 `hedgeDelayMs` 调大或设 0（关）。
