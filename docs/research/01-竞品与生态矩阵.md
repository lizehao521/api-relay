# 竞品与生态矩阵

## 结论速览

1. 「API 中转站」赛道**早已不是清一色 OneAPI 套壳**：LiteLLM（58.5k★）、NewAPI（47.8k★）、Portkey（13.0k★）、Helicone 已把路由/故障转移/可观测做成成熟产品，我们要竞争的是一条**已被工程化过**的赛道。
2. **重大事实更正**：`Calcium-Ion/new-api` 已迁移至 `QuantumNous/new-api`，且许可证从「OneAPI 的 MIT 派生」变为 **AGPL-3.0 + Section 7 附加条款**（必须保留 UI 署名与项目链接）。这直接否决「fork NewAPI 闭源商用」这条路径。
3. **P3 失败归因不是全空白，但空白位比预想的更窄也更值钱**：OpenRouter 已给出行业最强的**机器可读类型化错误**（`error_type` 词表 + `provider_code` + `metadata.raw` + `Retry-After` + 中途流式错误事件），LiteLLM 已给出**异常类型映射 + RateLimitErrorCategory（上游限流 vs 自身限流）**。真正没人做的是：**把错误翻译成面向 Agent 的「可执行下一步」（suggested_next / quick_action）**，以及把这份归因**跨上游统一成稳定口径并产品化**。
4. **OneAPI 根本没有「多上游 key 池」**：`model.Channel.Key` 是单个 `string` 字段（`model/channel.go:23`），一渠道一 key；多 key 轮换是 NewAPI 的增量（`GetNextEnabledKey` / `handlerMultiKeyUpdate`）。原评估文档把「多上游 key 池」当作中转站标配，需要按项目区分。
5. **降损层（P2/P3/P8）的嵌入难度排序是 LiteLLM ≪ NewAPI < OneAPI ≪ Portkey/Cloudflare**：LiteLLM 自带 `async_post_call_failure_hook`，就是一个现成的 P3 插槽；OneAPI/NewAPI 必须改 `controller/relay.go` 这条关键路径，属于「侵入式二开」。
6. **自研结论：核心转发与计费自研（Go），降损层自研（独立进程/中间件），但错误模型与路由策略必须抄 OpenRouter/LiteLLM 的成熟口径**，不要自己发明 `error_type`。
7. **必须放弃**：把中转站做成 Agent 平台（工具编排、会话记忆、轨迹可视化）、响应改写类降损（P1/P6）、有状态意图栈（P4）——理由见第 E 节。
8. **成本红线**：NewAPI 的 AGPL 传染 + OneAPI 主分支停滞，使「fork 起量」的性价比显著低于 2024 年；建议以「自研核心 + 借鉴设计」为主路径。

## 1. 逐竞品剖析

### 1.1 songquanpeng/one-api（OneAPI）

**它是什么**
「LLM API 管理 & 分发系统」：把 OpenAI/Azure/Claude/Gemini/DeepSeek/豆包/文心/星火/通义/混元等统一成一套 OpenAI 兼容 API，用于 key 管理与二次分发；Go 单可执行文件 + Docker，自带 Web 管理与用户/令牌/渠道体系。`[E2][E3]`（README）

**架构与技术栈**
- Go + Gin + GORM；后端单体二进制；前端在 `web/`（React）。
- 渠道路由：内存缓存 `group → model → channels` 三级映射，按 **priority 分档 + 档内随机**（`model/cache.go:227 CacheGetRandomSatisfiedChannel`，`model/cache.go:238` 注释 "choose by priority"）。
- 上游适配器：`Adaptor` 接口 9 个方法 —— `Init / GetRequestURL / SetupRequestHeader / ConvertRequest / ConvertImageRequest / DoRequest / DoResponse / GetModelList / GetChannelName`（`relay/adaptor/interface.go:11-21`），在 `relay/adaptor.go:27 GetAdaptor(apiType)` 用 `switch` 硬编码分发（20+ 家）。

**已有能力** `[E3]`
- 多渠道负载均衡、`stream` 模式、多机部署、令牌管理（过期/额度/IP 白名单/模型白名单）、兑换码、渠道批量创建、用户分组 + 渠道分组 + 分组倍率、额度明细、失败自动重试、绘图接口、Cloudflare Turnstile、多种登录方式。
- 管理 API：README 第 118 条明确写「支持通过系统访问令牌调用管理 API，进而**在无需二开的情况下扩展和自定义**功能」——即**官方承认的扩展方式是管理 API，而非代码钩子**。

**错误归因与可观测：几乎没有** `[E1]`
- 上游错误处理唯一入口 `relay/controller/error.go:55 RelayErrorHandler`：把上游响应体反序列化成 `GeneralErrorResponse`（该结构同时兼容 `error.message`、`message`、`msg`、`err`、`error_msg`、`header.message`、`response.error.message` 七种方言，`relay/controller/error.go:14-28`）。
  - 若上游是 OpenAI 格式（`error.message != ""`）→ **原样覆盖**，上游的 `type`/`code` 被保留透传；
  - 否则 `ToMessage()` 只抽出**一个字符串**，塞进 `{message, type:"upstream_error", code:"bad_response_status_code", param:"<status>"}`（`relay/controller/error.go:66-99`）。
  - 结论：**结构保住了，语义（谁出错、哪一类）全丢了**。非 OpenAI 上游的失败在客户端看来永远长一样。
- 日志模型 `model.Log`（`model/log.go:15-32`）只有 `Content string`、`Quota`、`PromptTokens/CompletionTokens`、`ChannelId`、`RequestId`、`ElapsedTime`、`IsStream`——**没有 error_code / error_type / 上游 request id 字段**。
- 原始响应体只有在 `config.DebugEnabled` 时才写到系统日志（`relay/controller/error.go:79-81`），不进结构化存储。

**授权协议**
MIT（`LICENSE`，Copyright 2023 JustSong）。**可闭源商用、可 fork 改名、无传染**——这是它相对 NewAPI 的最大优势。

**我们能借鉴什么**
- `GeneralErrorResponse` 的「七方言兜底」思路值得抄：上游错误体格式极度不统一，**先兜住再收敛**。
- 渠道分组 + 分组倍率 = 分层定价（free/standard/pro）的现成字段模型。
- 「管理 API 即扩展点」的定位，说明它的用户根本不改代码——我们若做钩子，要面向**运维配置**而非面向开发者编程。

**我们不该重复造什么**
- 20+ 家上游适配器一家家手写。若自研，先做 **OpenAI 兼容上游直通**（覆盖 80% 中转需求），非兼容上游靠「转换适配器插件 + 社区」后置。
- 重做用户/令牌/兑换码/邀请/公告这套后台 CRUD——可以直接照抄数据模型（OneAPI 数据模型已是事实标准，NewAPI 明确「完全兼容原版 One API 数据库」）。

### 1.2 QuantumNous/new-api（原 Calcium-Ion/new-api）

**它是什么**
OneAPI 的增强分支，现已发展为「统一 AI 模型聚合与分发中枢」：跨协议互转（OpenAI ⇄ Claude ⇄ Gemini ⇄ Responses）、多渠道多 key、更完整的计费与看板。`[E2][E3]`

**⚠️ 三个必须先知道的事实**
1. **仓库已迁移**：`api.github.com/repos/Calcium-Ion/new-api` 返回 `301 Moved Permanently → /repositories/717197250`，解析后 `full_name = QuantumNous/new-api`，homepage 为 `https://www.newapi.ai`。README 中的 badge 与配套工具链接仍指向 `Calcium-Ion/...`（旧路径），存在混用。`[E2][E1]`
2. **许可证是 AGPL-3.0，且带 Section 7 附加条款**。README 原文：修改版本必须保留署名 `Frontend design and development by New API contributors.`，且**任何带 UI 的修改版本必须保留指向 `https://github.com/QuantumNous/new-api` 的可见链接**。`[E1]`（`README.md:474-488`）
3. README 明确写「本项目基于 One API（MIT）开发」，同时提供 `support@quantumnous.com` 作为「不想遵守 AGPL 义务」的商业联系入口——即**双重授权模式**。`[E1]`

**架构与技术栈** `[E1]`
- Go；`model/`（GORM）、`relay/`（转发）、`relaykit/`（**已抽成独立模块**：`relaykit/dto`、`relaykit/types`、`relaykit/relayconvert`）、`service/`（计费与错误服务）、`middleware/`、`plugins/`（内置任务插件）、`web/`、`electron/`。
- 多 key 池：`Channel` 支持多 key + 每 key 独立状态。`model/channel.go:204 GetNextEnabledKey()`、`model/channel.go:671 handlerMultiKeyUpdate(channel, usingKey, status, reason)`、`model/channel.go:723 hasEnabledMultiKey(keys, statusList)`。**这是 OneAPI 没有的能力，也是「多上游密钥池」这一列在国产中转项目里的唯一实现。**
- 内部错误类型 `types.NewAPIError`（`relaykit/types/error.go:90`）：字段含 `Err / RelayError / skipRetry / recordErrorLog / errorType / errorCode / StatusCode / Metadata`，并实现 `Unwrap()` 以支持 `errors.Is/As`。`[E1]`

**已有能力** `[E3]`
- 智能路由：**渠道加权随机 + 失败自动重试 + 用户级模型限流**（README.zh_CN「智能路由」节）。
- 计费：分组倍率、按次/按量/缓存命中成本核算、`OpenAI/Azure/DeepSeek/Claude/Qwen` 缓存计费统计。
- 格式转换：Compatible ⇄ Claude Messages、Compatible → Gemini、Gemini → Compatible、Compatible ⇄ Responses（标注开发中）、reasoning effort、思考转内容。
- 高级 API：Responses、Realtime（含 Azure）、Claude Messages、Gemini、Rerank。
- 数据看板（可视化控制台 + 统计分析）、多语言、权限管理。
- 重试配置暴露到运营设置：`设置 → 运营设置 → 通用设置 → 失败重试次数`；`ERROR_LOG_ENABLED` 环境变量（默认 `false`）控制错误日志。

**错误归因与可观测：明显强于 OneAPI，但仍不面向 Agent** `[E1]`
- 错误处理入口 `service/error.go:87 RelayErrorHandler(ctx, resp, showBodyWhenFail)`：与 OneAPI 同构，但**多了一层内部错误码**：
  - 上游错误体是 object → `TryToOpenAIError()` 成功则 `types.WithOpenAIError(oaiError, status)`（上游 `code` 透传）；
  - 否则 `types.NewOpenAIError(errors.New(message), types.ErrorCodeBadResponseStatusCode, status)`。
- **内部 `ErrorCode` 词表**（`relaykit/types/error.go:40-88`）已相当细：`channel:no_available_key`、`channel:invalid_key`、`channel:response_time_exceeded`、`channel:model_mapped_error`、`bad_response_status_code`、`empty_response`、`prompt_blocked`、`sensitive_words_detected`、`insufficient_user_quota`、`pre_consume_token_quota_failed`、`count_token_failed`、`access_denied` …；`ErrorType` 则区分 `openai_error / claude_error / gemini_error / upstream_error / new_api_error`。
- **对外映射是「有损」的**：`ToOpenAIError()`（`relaykit/types/error.go:180`）在 `errorType == openai_error` 时**直接返回上游原始错误**（上游语义保留），其他情况填 `type = errorType`、`code = errorCode`。也就是说**内部细分错误码并没有完整暴露给客户端**。
- **主动脱敏**：`MaskSensitiveInfo`（`relaykit/relayconvert/kitutil/mask.go:65`）会把错误消息里的 URL host/path 打码；`MaskSensitiveErrorWithStatusCode()` 用于日志。**这是一条与 P3 直接冲突的设计选择**：为了防泄漏，归因所需的上游细节被主动擦掉。
- 错误日志：`LogTypeError = 5`（`model/log.go:90`），`model/log.go:278 RecordErrorLog(...)`，由 `controller/relay.go:407` 的 `constant.ErrorLogEnabled && types.IsRecordErrorLog(err)` 控制；`controller/relay.go:428` 记录 `MaskSensitiveErrorWithStatusCode()`。
- **`Log.UpstreamRequestId`（`model/log.go:79`）**：记录上游请求 id，这是**对账/追责**的关键字段，OneAPI 没有。这已经是一个 P3 归因的基础设施雏形，只是没有做「下一步该做什么」。
- 重试判定已从「纯看状态码」升级为「看错误类型」：`controller/relay.go:365 shouldRetry(c, openaiErr, retryTimes)` 依次判断 `IsChannelError` → 重试、`IsSkipRetryError` → 不重试、`GetChannelConstraints().SuppressesRetry()`、`operation_setting.IsAlwaysSkipRetryCode(errorCode)`、`ShouldRetryByStatusCode(code)`。

**授权协议**
**AGPL-3.0 + Section 7**，另有商业授权入口。`[E1]`

**我们能借鉴什么**
- **`ErrorCode` 分层命名法**（`channel:*` / `client:*` / `response:*` / `quota:*`）比 OpenRouter 的扁平词表更适合**内部运维**：一眼看出是「渠道问题」还是「用户请求问题」还是「配额问题」。建议我们的错误模型**内部用分层码，外部映射成 OpenRouter 风格扁平 `error_type`**。
- **`skipRetry` / `recordErrorLog` 作为错误对象的元属性**（而不是在调用点用 if 判断），非常干净，值得抄。
- `UpstreamRequestId` 落日志 = 与上游对账的抓手。
- 多 key 池的 key 级状态机（`handlerMultiKeyUpdate`）。

**我们不该重复造什么**
- 协议互转（Claude Messages / Gemini / Responses）在 MVP 阶段不做：CloseAI 的文档已证明这件事在国内中转站是标配，但它对「P3 归因 + 分层计费」这个差异化点毫无贡献，是纯粹的上游适配工作量。
- 不要 fork NewAPI 代码：AGPL 传染 + UI 署名义务 + 上游还在高速迭代（2026-09-09 仍有提交）。

### 1.3 BerriAI/litellm（含 proxy 模式、router fallback/retry、错误映射）

**它是什么**
「The fastest, litest AI Gateway. Rust core with Python SDK. Call 100+ LLM APIs in OpenAI (or native) format with cost tracking, guardrails, load balancing, and logging」——既是 **Python SDK**（统一调用 100+ 上游），也是 **Proxy/网关**（`litellm/proxy`，带虚 key、预算、限流、管理面板）。`[E2]`

**架构与技术栈** `[E1]`
- Python 主体；核心为 SDK + FastAPI Proxy；`litellm/router.py` 是路由中枢；`litellm/litellm_core_utils/exception_mapping_utils.py`（2736 行）是异常映射中枢；`litellm/integrations/custom_logger.py` 是钩子系统；`litellm/proxy/hooks/` 是一堆内置钩子（20+ 个）。
- 管理后台：`litellm/proxy/proxy_server.py:890` 挂载 `/ui`（`app.mount("/ui", StaticFiles(directory=ui_path, html=True))`，`:2115`），默认运行时路径 `/var/lib/litellm/ui`（`:1984`）。**✅ 有后台。**

**已有能力** `[E1]`
- **路由策略**（`litellm/types/router.py:893 RoutingStrategy`）：`least-busy`、`latency-based-routing`、`cost-based-routing`、`usage-based-routing`(v2)、`provider-budget-routing`。这是所有竞品里**最完整的策略矩阵**。
- **重试/降载**：`num_retries`（默认 `openai.DEFAULT_MAX_RETRIES`）、`allowed_fails`（连续失败多少次进入冷却）、`cooldown_time`、`CooldownCache`（`litellm/router.py:972-997`）。
- **回退链**：`async_function_with_fallbacks`（`router.py:7527`）+ `async_function_with_fallbacks_common_utils`（`router.py:7271`），区分 **generic fallbacks / context_window_fallbacks / content_policy_fallbacks**，并有 `max_fallbacks` / `fallback_depth` 防回退地狱。
- **可重试判定**：`should_retry_this_error`（`router.py:7892`）——按异常类型决策，而不是按状态码：命中 `ContextWindowExceededError` 且有专用 fallback → 直接抛；`NotFoundError` → 抛；`RateLimitError` 且无健康部署但有 fallback → 抛；`AuthenticationError/PermissionDeniedError` 且只有 1 个部署 → 抛。
- **护栏**：`litellm/proxy/guardrails/`（`guardrail_hooks`、`guardrail_registry`、`init_guardrails`）+ 内置 `prompt_injection_detection.py`、`azure_content_safety.py`、`sensitive_data_routing.py`、Presidio PII。
- 计费与预算：`max_budget_limiter`、`dynamic_rate_limiter_v3`、`parallel_request_limiter_v3`、按 key/team/user/model 的 RPM/TPM。

**错误归因与可观测：这是全场最强的「归因地基」** `[E1]`
- `exception_mapping_utils.py:2323 exception_type(model, original_exception, custom_llm_provider, ...)` 把任意上游异常**映射成 OpenAI 异常格式**，并附带 `Model:`、`API Base:`、`Messages:`（前若干字符）、`num_retries`、`vertex_project/location`、`model_group`、`deployment` 等上下文。
- **类型化异常层级**（`litellm/exceptions.py`，共 **31 个** `class`，全部继承 `openai.*` 对应异常）：`AuthenticationError`、`NotFoundError`、`BadRequestError`、`Timeout`、`PermissionDeniedError`、`RateLimitError`、`ServiceUnavailableError`、`BadGatewayError`、`InternalServerError`、`APIError`、`APIConnectionError`、`JSONSchemaValidationError`、`UnsupportedParamsError`、`BudgetExceededError`、`GuardrailRaisedException`、`MidStreamFallbackError`、`ModifyResponseException`、`SensitiveDataRouteException`——**共 31 个语义化异常类（含 2 个枚举 `RateLimitErrorCategory`/`RateLimitType`）**，且**刻意挂在 openai 的异常树上**，让 `except openai.RateLimitError` 直接可用。

### 1.6 OpenRouter（商业聚合站）

**它是什么**
商业模型聚合与路由平台：一个 key 访问数百模型，按 provider 路由，按 token 计费，带 credits 体系。**它定义了本行业事实上的「错误契约」标准。** `[E3]`

**已有能力（错误与路由口径部分）** `[E3]`

**(a) provider routing 控制面**（`/docs/guides/routing/provider-selection`）
| 参数 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `allow_fallbacks` | boolean | `true` | 主 provider 不可用时是否允许备份 provider |
| `require_parameters` | boolean | `false` | 只路由到支持你全部参数的 provider |
| `data_collection` | `"allow"\|"deny"` | `"allow"` | 只路由到符合数据政策的 provider |
| `quantizations` | string[] | — | 按量化等级过滤（int4/int8…） |
| `sort` | string \| object | — | 按 `price` / `throughput` / `latency` 排序，支持 `by` + `partition` |
| `max_price` | object | — | 本请求可接受的最高价 |

- **`:nitro`** = 按吞吐排序 + **允许 priority 服务层级**端点；**`:floor`** = 按价格排序 + 允许 flex 层。两者是 `provider.sort` 的**超集**（sort 只排序，变体还放行对应层级端点）。`[E3]`
- `:nitro`/`:floor` 在设置了 `provider.order` 或 `service_tier:"default"` 时失效——**路由控制项之间存在互斥，这点文档写得很清楚，值得抄**。

**(b) 类型化错误契约**（`/docs/api-reference/errors-and-debugging`）——**本文最重要的一节**
- HTTP 状态码口径：`400 / 401 / 402 / 403 / 408 / 429 / 502 / 503`（402 用于「余额/credits 不足」，403 用于「权限不足 / 护栏拦截 / 内容审核命中」）。
- `429` 与 `503` **可能带标准 `Retry-After` 头**（秒），且官方明确 OpenAI/Anthropic/Vercel SDK 已自动遵守。
- **类型化错误码 `error.metadata.error_type`**（非流式响应体与流式 SSE 事件上都有），部分词表：
  - 400 类：`context_length_exceeded`、`max_tokens_exceeded`、`token_limit_exceeded`、`string_too_long`、`invalid_request`、`invalid_prompt`、`invalid_image`、`image_too_large`、`image_too_small`、`unsupported_image_format`、`image_download_failed`
  - 401/402/403 类：`authentication`、`permission_denied`、`payment_required`、`content_policy_violation`、`refusal`
  - 429/5xx 类：`rate_limit_exceeded`、`provider_overloaded`(503)、`provider_unavailable`(502)、`server`(500)、`unmapped`(500，上游错误无法归类时)
- **归因字段**：`error.metadata.provider_name`、`provider_code`（上游原始错误码）、`raw`（上游逐字载荷）。
- **脱敏策略**：**500 类错误**会把 `message` 换成通用文案、**省略 `provider_code` 与 `openrouter_metadata`**（防上游细节泄漏），但 `error_type` 仍为 `server`。非 500 才透出 `provider_code`。
- **内容审核错误专用结构** `ModerationErrorMetadata`：`{reasons[], flagged_input（截断到 100 字符，中间省略）, provider_name, model_slug}`。
- **护栏拦截**：403 + `metadata.patterns`（如 `["ignore all previous instructions"]`）；订阅 `X-OpenRouter-Experimental-Metadata: enabled` 后还会带 `openrouter_metadata.pipeline[]`，**列出跑过哪些护栏阶段**。
- **中途流式错误**（最有工程价值的一条）：SSE 事件 `{id, object:'chat.completion.chunk', created, model, provider, error:{code,message,metadata}, choices:[{delta:{content:''}, finish_reason:'error'}]}`，**HTTP 状态保持 200**（因为响应头早已发出），错误在 body 里；流在该事件后终止。
- **非流式也一样**：provider 已返回头之后才失败时，客户端拿到 `200 OK` 但 body 里**只有 `error` 对象、没有 `choices`**，官方要求「**即使 200 也要检查 body 里的 error 字段**」。
- **静默重试**：若失败发生在任何 token 到达客户端之前，OpenRouter 会自动换 provider 重试；**因为 200 已发出，即使所有 provider 都失败，状态码仍是 200**，最后一个错误在 body 里到达你。
- 其他：`models: [...]` 数组 = 模型级回退链（`/docs/guides/routing/model-fallbacks`）；`service_tier` 支持 `flex`（半价、更高延迟）/`priority`（`fast` 是其别名），**按实际服务的端点计费**，flex 不会回退到 standard（「那会比你要的层级更贵」），flex 容量不足时直接暴露错误。

**授权协议**
**闭源商业服务**（无开源仓库）。`[E2]`（GitHub 上无对应官方仓库）

**我们能借鉴什么**
- **直接采用它的 `error_type` 词表与 HTTP 口径**，不要自创。理由：OpenAI SDK 生态已按这套语义写 `except` 分支，我们自创一套等于让用户改代码。
- **200 + body 内 error + `finish_reason:"error"`** 的中途失败表达法——这是**流式场景唯一不破坏协议的做法**，我们必须实现。
- **500 类脱敏、非 500 透出 `provider_code`** 的折中策略：与 NewAPI 的 `MaskSensitiveInfo` 是同一思路。
- `X-...-Metadata` 可选头开启路由明细（选中的 provider、回退尝试次数）——**这就是「可验证透传」的产品化形态**，正好回应原评估文档 §7.1 的「可验证」诉求。
- 402 表示「余额不足」而不是 403——分层计费产品的正确状态码选择。

**我们不该重复造什么**
- 不要做模型市场/排行榜/chat 页面。
- 不要自研 `service_tier` 的灵活层语义（那需要跟上游谈容量分级）。

**(a) CloseAI（`closeai-asia.com`）——资料充足** `[E3]`

- **定位**：自称「国内第一家 API 中转平台」（原名 OpenAI Asia，2023-03-25 上线），面向企业与高校科研，「100% 官转」。

### 1.9 错误契约库：openai-python 的 APIError 层级（`openai==3.13.0`）

**它是什么**
OpenAI 官方 Python SDK 的异常契约；它是**事实上的客户端消费标准**——我们返回的错误体最终会被这个层析构。`[E1]`

**层级结构**（`src/openai/_exceptions.py`）
```
OpenAIError(Exception)
├── APIError                       ← 有 body/code/param/type/request
│   ├── APIResponseValidationError
│   ├── APIStatusError             ← 有 status_code / response
│   │   ├── BadRequestError            (400)
│   │   ├── AuthenticationError        (401)
│   │   │   └── OAuthError
│   │   ├── PermissionDeniedError      (403)
│   │   ├── NotFoundError              (404)
│   │   ├── ConflictError              (409)
│   │   ├── UnprocessableEntityError   (422)
│   │   ├── RateLimitError             (429)
│   │   └── InternalServerError        (>=500)
│   └── APIConnectionError
│       └── APITimeoutError
├── LengthFinishReasonError            ← 语义错误，不是 HTTP 错误
├── ContentFilterFinishReasonError     ← 内容过滤，不是 HTTP 错误
├── SubjectTokenProviderError
├── InvalidWebhookSignatureError(ValueError)
├── WebSocketConnectionClosedError
└── WebSocketQueueFullError
```

**关键工程含义（这是本文对 P3 最直接的一条设计约束）**
1. `APIError` 从 body 里只取三个字段：`body["code"]` → `self.code`、`body["param"]` → `self.param`、`body["type"]` → `self.type`（`_exceptions.py:70-79`）。**任何我们想传达给客户端的归因信息，只有两条路：塞进这三个字段，或者塞进 `body` 的其他键（`APIError.body` 完整保留原始 body）。**
2. **`ContentFilterFinishReasonError` 和 `LengthFinishReasonError` 不是 APIStatusError**，它们是「HTTP 200 但 finish_reason 异常」的语义异常。这说明：**内容过滤与长度截断在客户端是被当作「成功响应里的语义事件」处理的，而不是 HTTP 错误**。我们的 P3 归因层必须**同时覆盖 HTTP 错误路径和 200 响应里的 finish_reason 路径**，否则会漏掉一整类失败。
3. LiteLLM 的 30 个异常类**刻意继承 openai 的对应类**（`class RateLimitError(openai.RateLimitError)` 等），目的就是让用户的 `except openai.RateLimitError` 继续生效。**我们要兼容的「错误契约」就是这张表，不是 OneAPI 的 `model.Error`。**

## B. 「错误路径」现状：原样透传还是有加工？P3 到底空不空？

### B.1 OneAPI 的错误结构（源码级）

**唯一入口**：`relay/controller/error.go:55 RelayErrorHandler(resp *http.Response) *model.ErrorWithStatusCode`

**输出结构**（`relay/model/misc.go:17-27`）：
```go
type Error struct {
    Message string `json:"message"`
    Type    string `json:"type"`
    Param   string `json:"param"`
    Code    any    `json:"code"`
}
type ErrorWithStatusCode struct {
    Error
    StatusCode int `json:"status_code"`
}
```

**两种路径**：
| 上游错误体形态 | 结果 | 语义是否保留 |
|---|---|---|
| OpenAI 格式（`error.message != ""`） | `ErrorWithStatusCode.Error = errResponse.Error`（**整个上游 error 对象覆盖**，`error.go:91-93`） | ✅ 上游 `type`/`code` 透传 |
| 其他七种方言之一 | `ErrorWithStatusCode.Error.Message = errResponse.ToMessage()`，`Type` 保持 `"upstream_error"`，`Code` 保持 `"bad_response_status_code"`，`Param` = 状态码字符串（`error.go:66-99`） | ❌ **只剩一个字符串，谁错的、错在哪类全丢** |
| 连 `error.message` 都抽不出 | `"bad response status code %d"` | ❌ 完全丢失 |

**旁证**：OneAPI 自己产生的错误统一为 `{Type: "one_api_error", Code: <code>}`（`relay/adaptor/openai/util.go:11 ErrorWrapper`）。

**最终回给客户端**（`controller/relay.go:88-95`）：
```go
if bizErr.StatusCode == http.StatusTooManyRequests {
    bizErr.Error.Message = "当前分组上游负载已饱和，请稍后再试"   // 429 被统一改写成一句中文
}
bizErr.Error.Message = helper.MessageWithRequestId(bizErr.Error.Message, requestId)
c.JSON(bizErr.StatusCode, gin.H{"error": bizErr.Error})
```
> **注意源码里那行注释 `// BUG: bizErr is in race condition`（`controller/relay.go:91`）就写在错误回写路径上。** 这是上游已知的并发缺陷，也是我们自研时要避开的同类问题（重试循环里共享了 `bizErr` 指针）。

**结论**：OneAPI 对错误**几乎没有加工，是「透传 + 兜底 + 把 429 翻译成一句固定中文」**。`Retry-After`、上游 request id、错误类别**一律不进响应**。

### B.2 NewAPI 的错误结构（源码级）

**入口**：`service/error.go:87 RelayErrorHandler(ctx, resp, showBodyWhenFail) *types.NewAPIError`

**内部错误对象** `types.NewAPIError`（`relaykit/types/error.go:90`）：
```go
type NewAPIError struct {
    Err            error
    RelayError     any             // 原始上游 error 对象（OpenAIError / ClaudeError …）
    skipRetry      bool
    recordErrorLog *bool
    errorType      ErrorType       // openai_error | claude_error | gemini_error | upstream_error | new_api_error …
    errorCode      ErrorCode       // 30+ 个分层错误码
    StatusCode     int
    Metadata       json.RawMessage // 从上游 OpenAIError 透传（error.go:339）
}
```

**对外映射** `ToOpenAIError()`（`relaykit/types/error.go:180-212`）：
- `errorType == openai_error` → **原样返回上游 OpenAIError**（含 `metadata`）；
- `errorType == claude_error` → 转成 `{message, type: claudeError.Type, param:"", code: errorCode}`；
- 其他 → `{message, type: string(errorType), param:"", code: errorCode}`。
- **然后统一走 `MaskSensitiveInfo(result.Message)` 脱敏**（`count_token_failed` 除外）。

**结论**：NewAPI 的错误路径是**「透传 + 内部强类型化 + 对外有损 + 主动脱敏」**：
- 它**内部知道**是 `channel:invalid_key` 还是 `channel:response_time_exceeded`（已具备归因能力）；
- 但**对外只保留上游原始错误或一个粗粒度 `errorCode`**，且消息里的 URL/host/path 被打码；
- **完全没有**「建议下一步」「可重试性提示」「预计恢复时间」这类字段。

### B.4 论证：P3 失败归因**不是空白位，但真正的空白更窄**

原评估文档 §3.2 写：「把 raw error 变成 `{failure_reason, suggested_next, quick_action}` 卡片……**这是所有中转站里独一份的卖点**」。**这个判断需要修正，但不推翻它的结论。**

**已被别人做掉的部分（我们不能声称「业内没人做」）**：
1. **错误分类（who/what）**：OpenRouter 的 `error_type` 词表是事实标准；LiteLLM 的 30 类异常 + `RateLimitErrorCategory`（上游限流 vs 自身限流）比「分类」还多走了一步——它回答了「**是谁**限流」。
2. **上游归因信息透出**：OpenRouter 的 `provider_code` / `provider_name` / `metadata.raw`；LiteLLM 的 `provider_specific_fields`；NewAPI 的 `Metadata` 透传与 `UpstreamRequestId` 落库。
3. **可重试性提示**：OpenRouter 的 `Retry-After` 头 + 官方明确「OpenAI/Anthropic/Vercel SDK 已自动遵守」。
4. **中途流式失败的规范化表达**：OpenRouter 的 `200 + error + finish_reason:"error"`。
5. **脱敏策略**：OpenRouter（500 才脱敏）、NewAPI（`MaskSensitiveInfo` 打码 URL）。

**仍然是空白的部分（P3 的真实价值区间）**：
1. **`suggested_next` / `quick_action`**：**没有任何一家**给出「下一步该调什么」。LiteLLM 最接近，但它的输出是「换 deployment / 走另一条 fallback 链」的**机器决策**，不是**给 Agent/开发者看的自然语言可执行建议**。
2. **跨上游的稳定归因口径 + 面向 Agent 的语义**：OpenRouter 的词表是**面向人类与 SDK 的扁平分类**，没有「这个失败是**可自愈**的（退避重试即可）还是**需要改请求**的（缩上下文/改 prompt/换模型）」这一层——而这恰恰是 Agent 最需要的决策输入。
3. **失败成本的可视化**：CloseAI 已经知道「400 错误扣数倍限流配额」，但**没人把「你这次失败浪费了什么」告诉用户**。这是 P8 与 P3 的交汇点。
4. **国内套壳站（OneAPI/NewAPI 派生的绝大多数站点）**：确实**一个都没做**——原评估文档的这句判断在这些站点上是成立的。

**修正后的结论（写进产品定位）**：
> 不能说「失败归因是业内空白」。应说：**「错误的类型化」已经是行业标配且 OpenRouter 已定标准；「错误的可执行化」（failure_reason → recoverable? → quick_action，并覆盖 200-with-error 与 finish_reason 两条路径）仍是空白，且国内套壳站连类型化都没有。** 我们的差异化必须落在**可执行化 + 跨上游统一口径**，而不是「我们会分类错误」——后者是 2026 年的入场券，不是卖点。

**同时必须接受的一条约束**：NewAPI 的 `MaskSensitiveInfo` 说明「脱敏」与「归因」存在**真实张力**。我们的 P3 必须设计成**分级暴露**：`standard` 层只给类型与建议（不给上游原文），`pro` 层才给 `provider_code`/`raw`——这也正好与分层商业模式对齐。

## C. 扩展点评估：想在这些项目上二开，钩子在哪、代价是什么

### C.1 OneAPI：**没有钩子，只有接口和中间件**

| 想做 | 要改哪里 | 代价 |
|---|---|---|
| 加 P3 归因 | `relay/controller/error.go:55 RelayErrorHandler`（构造错误对象）+ `controller/relay.go:88-95`（回写响应） | ✅ 改动点集中，**两个文件**。但会与上游升级冲突 |
| 加 P2 预检 | 请求入口，需在 `controller/relay.go:Relay()` 之前插一层；最自然的位置是 `relay/controller/helper.go` 或新增 middleware | ⚠️ 需要拿到 body 且不能破坏 `GetRequestBody(c)` 的复用（重试要靠它重放 body） |
| 加路由策略 | `model/cache.go:227 CacheGetRandomSatisfiedChannel`（priority 分档 + 随机） | ⚠️ 想加 latency/cost 路由 = 重写整个选择器 |
| 加新上游 | 实现 `relay/adaptor/interface.go:11 Adaptor` 9 个方法 **+ 在 `relay/adaptor.go:27 GetAdaptor` 的 switch 里加 case + 在 `relay/apitype` 加常量 + 前端加渠道类型** | ❌ **至少 4 处硬编码**，无法插件化 |
| 加多 key 池 | 改 `model.Channel.Key` 字段类型 + 迁移 + 全部引用点 | ❌ 伤筋动骨（NewAPI 花了一整个分支做这件事） |
| 外部扩展 | 管理 API（README 第 118 条） | ⚠️ 只能做「管理面扩展」，**碰不到转发路径**，做不了 P2/P3 |

**总体代价**：**中**。改动点集中且代码量小（Go，单二进制），但**没有任何官方扩展机制**，所有改动都是 fork diff，且上游主分支已停滞——好处是「不会天天冲突」，坏处是「永远得不到上游修复」。

### C.2 NewAPI：**有两层扩展点，但核心路径仍要改**

| 扩展点 | 位置 | 能力 |
|---|---|---|
| ① 错误对象扩展 | `relaykit/types/error.go`（`NewAPIError` + `ErrorCode` 常量） | ✅ **最干净的插入点**：加一个 `suggestion`/`recoverable` 字段 + 一个新 `ErrorCode`，然后在 `ToOpenAIError()` 里映射出去 |
| ② 失败钩子 | `service/error.go:87 RelayErrorHandler` + `controller/relay.go:365 shouldRetry` | ✅ 归因逻辑可以只在 `RelayErrorHandler` 出口做，**不侵入重试循环** |
| ③ 错误日志 | `model/log.go:278 RecordErrorLog` + `controller/relay.go:428` | ✅ P8 度量的天然埋点，已有 `LogTypeError` + `UpstreamRequestId` |
| ④ 请求预检 | `middleware/` 目录（已有 `distributor.go` / `rate-limit.go` / `model-rate-limit.go` 等 20+ 个中间件） | ✅ **加一个 Gin middleware 即可**，是 P2 的最佳落点，且天然 fail-open（返回 `c.Next()`） |
| ⑤ 转发中间件 | `relay/relay_adaptor.go`、`relay/plugin_protocol.go`、`plugins/tasks/*/plugin.js` | ⚠️ 任务插件协议很复杂（`PluginProtocolLimits` 设了 12 项上限：`MaxEventsPerTick`、`MaxStateBytes`、`MaxOutputBytes`…），是为**视频/任务类异步插件**设计的，**不适合拿来做 P3** |
| ⑥ 渠道选择/多 key | `model/channel.go:204 GetNextEnabledKey`、`middleware/distributor.go` | ✅ 路由策略可在这里加 |
| ⑦ 协议转换 | `relaykit/relayconvert/` | ⚠️ 不需要碰 |

**总体代价**：**中低（技术上）／高（法律上）**。技术上 NewAPI 是**四个项目里最适合挂 P3/P8 的**（错误对象已经是强类型、日志已有 error 类型、中间件体系完备）。但 **AGPL-3.0 + Section 7** 意味着：只要我们把 NewAPI 的代码跑成面向用户的服务，就必须**向用户提供完整对应源码**，且**UI 必须保留 NewAPI 署名与项目链接**——这直接摧毁「做一个自有品牌的中转站」这件事。

### C.3 LiteLLM：**钩子最丰富，P3 有现成插槽**

| 扩展点 | 位置 | 能力 |
|---|---|---|
| **`async_post_call_failure_hook`** | `litellm/integrations/custom_logger.py:451` | ✅✅ **P3 的现成插槽**。签名 `(request_data, original_exception, user_api_key_dict, traceback_str) → Optional[HTTPException]`，官方注释明写：*"Return an HTTPException to transform the error response sent to the client."* |
| `async_pre_call_hook` | `custom_logger.py:412` | ✅ P2 的落点（可 raise / 返回字符串拒绝 / 返回改写后的 dict） |
| `async_post_call_success_hook` | `custom_logger.py:472` | ⚠️ 可做 P1 类改写（我们不做） |
| `async_post_call_response_headers_hook` | `custom_logger.py:423` | ✅✅ **可注入自定义响应头**——这正是「暴露 `Retry-After` / `X-Failure-Reason`」的实现点 |
| `async_moderation_hook` | `custom_logger.py:488` | 护栏 |
| `async_filter_deployments` / `async_pre_routing_hook` | `custom_logger.py:265` / `:250` | ✅ 自定义路由 |
| `async_post_call_failure_deployment_hook` | `custom_logger.py:302` | ✅ 单 deployment 级失败处理 |
| 错误映射 | `litellm/litellm_core_utils/exception_mapping_utils.py:2323 exception_type()` | ⚠️ 2736 行的巨型函数，改它风险高（所有 provider 共用） |
| 代理错误体 | `litellm/proxy/_types.py:3913 ProxyException` + `proxy_server.py:1658 openai_exception_handler` | ⚠️ 源码注释 "DO NOT MODIFY THIS" |

**总体代价**：**低**。对一个会 Python 的团队，**P2/P3 可以做到零 fork**——写一个 `CustomLogger` 子类，实现 `async_pre_call_hook`（P2）与 `async_post_call_failure_hook`（P3），挂进 config 即可。P8 度量则用现成的 `async_log_success_event` / `async_log_failure_event` 回调。
**代价是**：核心是 Python（性能/内存占用不如 Go）、MIT 但 `enterprise/` 例外范围未核实、以及**你只是在它的产品上加了一层，护城河属于它**。

### C.4 Portkey Gateway：钩子类型单一，且配置在文件里

| 扩展点 | 位置 | 能力 |
|---|---|---|
| Hook 类型 | `src/middlewares/hooks/types.ts:112 HookType{GUARDRAIL, MUTATOR}`，事件仅 `beforeRequestHook`/`afterRequestHook`（`:109`） | ⚠️ 只有两个时机，**没有「失败后」这个时机** |
| 护栏插件 | `plugins/*/`（20+ 厂商）+ `plugins/index.ts` 静态注册表 | ❌ 加一个插件必须**改 `plugins/index.ts` 源码**并重新构建 |
| 超时/重试 | `src/handlers/retryHandler.ts` | ⚠️ 可加策略，但错误分类缺失 |
| 路由策略 | configs JSON（`strategy.mode` + `on_status_codes` + `targets`） | ✅ **改配置即可**，不用改代码 |

**总体代价**：**高**。Portkey **没有「失败后」钩子**，P3 归因只能插在 `responseHandlers`/`handlerUtils` 这类核心路径上，且它是 TypeScript 逐 provider 手工映射错误的架构，**没有统一归因层可供挂载**。要加 P3 = 从零给它补一个错误分类层，等于在别人家里盖房子。

### C.5 结论：扩展点质量排序

```
P2/P3 落地难度：  LiteLLM  ≪  NewAPI  <  OneAPI  ≪  Portkey / Cloudflare
法律风险：        OneAPI(LiteLLM/Portkey)   <   NewAPI(AGPL)
长期可控性：      自研  >  LiteLLM 挂载  >  OneAPI fork  >  NewAPI fork
```

## D. 自研 vs fork：最终对照表

| 维度 | 自研（Go 核心 + 独立降损层） | fork OneAPI（MIT） | fork NewAPI（AGPL） | 基于 LiteLLM 做插件层 |
|---|---|---|---|---|
| **起量速度** | ⚠️ 慢（2-4 周出可用转发+计费） | ✅ 最快（README 称 Docker 一键部署） | ✅ 最快 + 功能最全 | ✅ 快（网关能力现成） |
| **可控性** | ✅✅ 完全可控，错误模型/路由/计量一开始就按我们的设计 | ✅ 代码简单，两个文件就能改错误路径 | ⚠️ 代码体量大（33MB 浅克隆）、`relaykit` 已抽为独立模块且仍在演进（**此判断基于目录结构推断**）、上游高速迭代 | ⚠️ 受 Python 生态与上游节奏约束 |
| **降损层（P2/P3/P8）嵌入难度** | ✅ 设计期预留，不是「嵌入」而是「内建」 | ⚠️ 中：改 `RelayErrorHandler` + `Relay()` 两处 | ⚠️ 中低：`NewAPIError` 已是强类型 + middleware 体系完备 | ✅✅ `async_pre_call_hook` + `async_post_call_failure_hook` 零 fork |
| **上游同步成本** | ✅ 无（无上游） | ✅ 低（主分支事实停滞；代价是拿不到安全修复） | ❌ **高**（2026-09-09 仍有提交，`relaykit` 已抽为独立模块并仍在演进，AGPL 义务随代码走） | ⚠️ 中（跟版本升级，但钩子是稳定 API） |
| **许可与商用风险** | ✅ 最低（自有代码；注意上游 SDK 许可） | ✅ **MIT，可闭源商用** | ❌❌ **AGPL-3.0 + Section 7**：网络服务须提供对应源码、UI 须保留署名与项目链接；绕开需商业授权 | ⚠️ MIT（`enterprise/` 例外范围未核实）；Portkey/Helicone 同类可选 |
| **多上游 key 池** | 需自研（设计简单，但 key 级状态机 + 冷却要做对） | ❌ 没有（一渠道一 key） | ✅ 已有 | ✅ 已有（deployment 级） |
| **计费/额度/分层** | 需自研（但分层是我们的核心，必须自研） | ⚠️ 有额度/倍率，但无订阅制/分层 | ⚠️ 同上（且偏向「面向公众服务」的合规提示） | ⚠️ 有预算/虚 key，但订阅制需另做 |
| **可观测** | 需自研（P8 只需要少量指标，成本可控） | ❌ 只有 Log 表 | ⚠️ 有 `LogTypeError` + 看板，但仍需接 ClickHouse | ✅✅ 现成 |
| **品牌与信任** | ✅ 自有品牌，「我只是管道」的承诺可验证 | ⚠️ 需改名去 OneAPI 痕迹，用户界面/文档要重做 | ❌ UI 必须带 NewAPI 署名与链接 | ⚠️ 品牌是 LiteLLM 的 |

### D.1 建议路径（三选一，按资源排序）

**路径 A（推荐）：自研核心 + 借鉴错误契约**
- Go 核心：转发 + 渠道路由 + key 池 + 令牌/额度/分层计费。
- 错误契约**直接采用 OpenRouter 的 `error_type` 词表**，内部再叠一层 NewAPI 式分层码（`channel:*` / `client:*` / `response:*` / `quota:*`）用于运维。
- 降损层（P2/P3/P8）**做成进程内 middleware + 独立度量管道**，从第一天就设计在请求路径上，而不是事后插入。
- **不引入任何 AGPL 代码**；可参考 OneAPI 的数据模型（MIT，可安全借鉴）与 NewAPI 的设计思路（**只读设计，不复制代码**）。

**路径 B（最快验证）：LiteLLM 插件层做 MVP 验证 P3 假设**
- 用 LiteLLM proxy 起一个网关，写一个 `CustomLogger` 实现 P2/P3，验证「归因卡片能否提升 Agent 任务完成率」这个**唯一真正未验证的产品假设**。
- 验证成功后，把结论搬回路径 A。
- 这一路径的产物是**实验**，不是产品——**不要用它上线**（品牌、性能、许可都不合适）。

**路径 C（不建议）：fork NewAPI**
- 唯一适用场景：你的产品**本来就打算开源**，且不介意 UI 上带 NewAPI 署名与链接。
- 在「按 token 计费 + 分层免费/标准/Pro」的商业化目标下，**这条路径与目标冲突**。

## E. 我们应刻意放弃 / 推迟的功能清单

原则：**中转站是管道，不是 Agent 平台。** 每条给出「为什么放弃」与「什么时候可以再看」。

### E.1 立刻放弃（做都不要做）

| 功能 | 放弃理由 | 证据/依据 |
|---|---|---|
| **P1 符号态提炼（服务端改写成功响应）** | 破坏「我只是管道」的信任假设；且中立数据流里全是符号数据，无可提炼 | 原评估文档 §4；NewAPI `MaskSensitiveInfo` 已证明「少暴露上游原文」才是行业共识方向 |
| **P6 符号态缓存（命中直接返回）** | 命中 = 0 收入；LLM 非确定性下陈旧结果 = 信任灾难 | 原评估文档 §3.3；OpenRouter 的 caching 属平台级且有明确语义 |
| **P4 跨 turn 意图栈** | 要求有状态架构；国内最大商业中转 CloseAI **明确不支持任何有状态接口**，是独立佐证 | CloseAI 文档：「不支持 file、fine-tune、assistants 等有状态接口」 |
| **P5 执行轨迹可视化** | 中转站只看得到单请求，看不到用户 Agent 的多步编排 | 原评估文档 §3.4 |
| **P7 同轮只读去重** | 没有「轮」的概念，是 Agent 框架层的事 | 原评估文档 §3.3 |
| **完整 LLM 可观测平台**（session/user/playground/evals/custom properties） | 那是 Helicone 的主场，做它等于换个赛道跟 6.1k★ 的对手打 | Helicone README 能力清单 |
| **模型市场/排行榜/Chat 页面** | 与「管道」定位冲突，且是 OpenRouter 的主场 | OpenRouter 站点结构 |
| **自研 20+ 上游适配器** | 纯工作量，无差异化；MVP 只需 OpenAI 兼容直通 | OneAPI `relay/adaptor/` 目录（20+ 家手写适配器） |
| **1400+ provider 生态 / 20+ 安全厂商护栏插件** | Portkey 的护城河，不是我们的 | Portkey `plugins/` 目录 |
| **DLP / 内容安全引擎** | 安全产品的活；我们最多做**前置敏感词 + 可选转调上游 moderations** | NewAPI 只做 `SensitiveWords`；Cloudflare DLP 是免费 Beta 但属安全产品 |
| **协议全家桶互转（Claude Messages / Gemini / Responses / Realtime / Rerank / 视频任务插件）** | 与 P3 差异化零关系；NewAPI 的 `plugin_protocol.go` 复杂度（12 项协议上限）就是前车之鉴 | NewAPI `relay/plugin_protocol.go:28 PluginProtocolLimits` |
| **做「不落盘用户 prompt」之外的隐私承诺** | 做不到就不承诺；应学 Cloudflare 给「只存元数据不存正文」的**显式开关** | `cf-aig-collect-log-payload` 头 |

### E.2 推迟（有明确触发条件再看）

| 功能 | 推迟到什么时候 | 触发条件 |
|---|---|---|
| **按延迟/成本动态路由** | 有 ≥2 个上游且已有真实 P8 数据 | 路由决策需要数据支撑；LiteLLM 的 5 种策略是「有数据之后」的产物 |
| **订阅制计费（Pro 层）** | 标准层跑通、有 ≥30 个稳定付费用户 | 原评估文档 §6.4 |
| **`:nitro`/`:floor` 式服务层级路由** | 与上游谈到容量分级 | OpenRouter 的实现依赖 priority/flex 容量层 |
| **可视化动态路由 + 版本回滚** | 路由规则超过 5 条、需要非研发人员维护时 | Cloudflare Dynamic Routing 的形态 |
| **ClickHouse 时序度量** | PostgreSQL 的聚合查询成为瓶颈 | 原评估文档 §8 已规划 |
| **多协议互转** | 有客户明确要求且愿意付费 | CloseAI 的「全模型聚合接口」是需求证明，但要客户付费验证 |
| **多 key 池的高级调度（key 级冷却/权重/健康分）** | 有 ≥3 个同渠道 key 时 | NewAPI `handlerMultiKeyUpdate` 的复杂度只有在多 key 场景才值得 |

### E.3 一条反向提醒：**不要放弃的东西**

以下三件事在竞品里被证明是「必须有」而不是「可选」，不要因为「自研从简」而砍掉：

1. **`Retry-After` 响应头**（OpenRouter 有，且主流 SDK 已自动遵守）——不加，用户的 SDK 重试就是瞎重试。
2. **`200 + body 内 error + finish_reason:"error"` 的中途流式失败表达**（OpenRouter 有）——不做，流式场景的失败就是静默断流。
3. **上游 request id 落库**（NewAPI `Log.UpstreamRequestId` 有）——不做，用户报障时你无法与上游对账。

这三件事**恰好都是「错误路径」的事**，也正好是 P3 的地基——它们同时证明了「P3 是入场券」和「P3 做成可执行建议才是差异化」。
