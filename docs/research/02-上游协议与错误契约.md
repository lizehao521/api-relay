## 1.3 SSE 帧格式规范（可直接抄）

### 1.3.1 线路格式

响应头：`Content-Type: text/event-stream`（OpenAI spec 中即为此值）。[V][R1]

每一帧：`data: {JSON}\n\n`。结束帧：`data: [DONE]\n\n`。
- 官方 spec 的流式示例逐帧内容（原样）[V][R1]：
  ```
  {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-6-astra", "system_fingerprint": "fp_44709d6fcb", "choices":[{"index":0,"delta":{"role":"assistant","content":""},"logprobs":null,"finish_reason":null}]}
  {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-6-astra", "system_fingerprint": "fp_44709d6fcb", "choices":[{"index":0,"delta":{"content":"Hello"},"logprobs":null,"finish_reason":null}]}
  {"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-6-astra", "system_fingerprint": "fp_44709d6fcb", "choices":[{"index":0,"delta":{},"logprobs":null,"finish_reason":"stop"}]}
  ```
- `data: [DONE]` 的书写形式由阿里云百炼兼容模式文档与 OpenRouter 文档共同确认 [V][R7][R10]。

### 1.3.2 chunk 字段契约

| 字段 | 语义 | 关键约束 |
|---|---|---|
| `id` | 完成 ID | **每个 chunk 必须完全相同**（spec：Each chunk has the same ID）[V][R1] |
| `created` | Unix 秒 | 每个 chunk 相同 [V][R1] |
| `model` | 模型名 | 每个 chunk 相同；见 1.8 陷阱表 |
| `object` | 固定 `chat.completion.chunk` | [V][R1] |
| `choices[].delta.role` | 通常仅首帧出现 | enum：`developer`/`system`/`user`/`assistant`/`tool` [V][R1] |
| `choices[].delta.content` | 增量文本 | string 或 null [V][R1] |
| `choices[].delta.tool_calls` | 增量工具调用 | 见 1.4.3 |
| `choices[].finish_reason` | 结束原因 | 非末帧为 null [V][R1] |
| `usage` | token 用量 | 未开 `include_usage` 时**可为 null 或整个字段缺失**；开启时非末帧为 `null` [V][R1] |
| `system_fingerprint` | 后端配置指纹 | 可为 null（DashScope 实测恒为 null）[V][R7] |

### 1.3.3 `usage` 在流中的出现时机（**P3 与计费实现的关键**）

官方 spec 对 `stream_options.include_usage` 的原文定义 [V][R1]：

1. 若设为 `true`，在 `data: [DONE]` **之前**额外流式发送一个 chunk；
2. 该 chunk 的 `usage` 字段是**整个请求**的 token 统计；
3. 该 chunk 的 `choices` 字段**恒为空数组**；
4. 其他所有 chunk 也会带 `usage` 字段，但值为 `null`；
5. **若流被中断，可能收不到这个最终 usage chunk**。

阿里云百炼兼容模式的实测输出完全吻合（末帧 `"choices":[],"usage":{"completion_tokens":16,"prompt_tokens":22,"total_tokens":38}`）[V][R7]。DashScope 未开启该选项时，普通 chunk 的 `"usage":null` [V][R7]。

`include_obfuscation`：默认开启，会在流式 delta 事件上附加随机 `obfuscation` 字段以规范化载荷长度；设为 `false` 可关闭。**中转站不应主动改变该行为**。[V][R1]

### 1.3.4 保活与超时

DeepSeek 明确说明：非流式请求会持续返回**空行**，流式请求会持续返回 **SSE 注释 `: keep-alive`**；这些不影响 JSON body 解析，但自行解析 HTTP 响应的实现必须正确处理。若推理 10 分钟未开始，服务端关闭连接。[V][R4]

**实现要求**：中转站自己的 SSE 解析必须（a）按空行分帧，（b）跳过 `:` 开头的注释行，（c）容忍空行填充。openai-node 的 `SSEDecoder` 实现即是此语义（`line.startsWith(':')` 直接返回 null）。[V][R12]

## 1.4 tool_calls / function calling 契约

### 1.4.1 请求侧

`tools: [{type:"function", function:{name, description?, parameters?, strict?}}]`，`type` 与 `function` 必需，`function.name` 必需，name 限 `a-zA-Z0-9_-`、最长 64。[V][R1]
`tool_choice`：`ChatCompletionToolChoiceOption`；`parallel_tool_calls`：布尔。[V][R1]
`functions` / `function_call` 为 deprecated 但仍存在于请求 schema 中，**必须透传不可丢弃**。[V][R1]

### 1.4.2 非流式响应侧

```json
"tool_calls": [{
  "id": "call_abc",
  "type": "function",
  "function": { "name": "get_current_weather", "arguments": "{\"location\":\"Boston\"}" }
}]
```
`ChatCompletionMessageToolCall` required：`id`, `type`, `function`；`type` enum 仅 `function`；`function` required：`name`, `arguments`。[V][R1]
**`arguments` 是字符串，不是对象**（模型可能生成非法 JSON，官方明确要求调用方自行校验）。[V][R1]

### 1.4.3 流式分片与拼接规则（可直接实现）

`ChatCompletionMessageToolCallChunk` required 仅 `index`；`id`、`type`、`function` 均为可选。[V][R1]

```
拼接算法（每个 choice 独立维护一个 map<index, ToolCall>）：
for chunk in stream:
  for tc in chunk.choices[0].delta.tool_calls ?? []:
     slot = map.get(tc.index) ?? { id: "", type: "function", function: { name: "", arguments: "" } }
     if tc.id        != null: slot.id = tc.id                    # 全量赋值，非拼接
     if tc.type      != null: slot.type = tc.type
     if tc.function?.name != null: slot.function.name += tc.function.name        # 字符串拼接
     if tc.function?.arguments != null: slot.function.arguments += tc.function.arguments  # 字符串拼接
     map.set(tc.index, slot)
```
规则来源：`index` 为必需字段说明其用于归并；`id` 在同一 tool call 的各分片中不会重复出现，故为赋值而非拼接；`function.name` 与 `function.arguments` 均声明为 string，官方语义是增量。[V][R1]

**硬约束**：
- 末帧 `finish_reason` 为 `"tool_calls"`（新旧 `function_call` 为 `"function_call"`）。[V][R1]
- **中转站必须逐 chunk 逐字节透传 `delta.tool_calls`，绝不可聚合成完整 tool_call 再下发**——聚合会把流式变非流式，破坏所有流式客户端。
- `index` 不可重编号，不可丢弃。

## 1.5 错误响应体标准形状

### 1.5.1 权威形状

```json
{ "error": { "message": "...", "type": "...", "param": null, "code": "..." } }
```
`Error` schema required 为 **`type`, `message`, `param`, `code` 四者全部必需**；`code` 与 `param` 类型为 `string | null`，`type` 与 `message` 为 `string`。`ErrorResponse` required 仅 `error`。[V][R1]

### 1.5.2 官方 SDK 实际读取位置（**决定中转站该把附加字段放哪里**）

- **openai-node**：`APIError.generate()` 先做 `const error = errorResponse?.['error']`，再从**该 `error` 对象内部**读 `code` / `param` / `type`。[V][R11]
- **openai-python**：`_make_status_error()` 先做 `data = body.get("error", body)`，再交给 `APIError`，从 `data` 内部读 `code` / `param` / `type`。[V][R13]
- 两者都从响应头 `x-request-id` 读 `requestID` / `request_id`。[V][R11][R13]

**结论（对 1.9 / 1.10 透传边界的直接约束）**：
1. `error` 对象**内部**的 `type` / `message` / `param` / `code` 会被 SDK 结构化读取，**不可省略、不可改名、不可把 null 换成缺失**。
2. 在 `error` 对象**内部**新增未知键（如 `relay_attribution`）不会被这两个 SDK 读取，也不会报错——但见 1.10 的取舍分析。
3. 在响应**顶层**新增键完全不进入 SDK 的 error 解析路径。

## 1.6 归因规则表（**P3 核心素材**）

### 1.6.1 匹配顺序（必须严格按此优先级）

1. **HTTP 状态码**（权威，最高优先）
2. **`error.code` 精确串匹配**（归一化到小写、去空格）
3. **`error.type` 精确串匹配**
4. **`error.message` 正则**（最后兜底）
5. 未命中 → `unknown`（fail-open，保持原始错误体透传）

### 1.6.2 枚举冻结

`failure_reason`（13 项，冻结）：

| 枚举值 | 中文语义 |
|---|---|
| `rate_limited` | 上游限流 |
| `quota_exhausted` | 余额/额度耗尽 |
| `auth_failed` | 鉴权失败 |
| `permission_denied` | 无权限/未开通 |
| `model_not_found` | 模型不存在 |
| `context_length_exceeded` | 超上下文 |
| `invalid_request` | 请求体非法 |
| `content_filtered` | 内容安全拦截 |
| `upstream_overloaded` | 上游过载 |
| `upstream_timeout` | 上游超时 |
| `upstream_unavailable` | 上游不可用/协议错误 |
| `client_disconnected` | 客户端断开 |
| `unknown` | 未归因 |

`quick_action`（7 项，冻结，与需求书一致）：`retry_with_backoff` / `reduce_context` / `switch_model` / `rewrite_input` / `top_up_balance` / `fix_request` / `abort`

`recoverable` 语义定义（**不要用「是否 5xx」判断**）：**原请求一字不改、只等一段时间重发，是否有可能成功**。`true` 仅当原因与请求内容无关。

### 1.6.3 规则表（按匹配顺序排列）

格式：`匹配条件 → failure_reason | recoverable | quick_action | suggested_next 模板`

#### 组 A — 鉴权与配额

| # | 匹配条件 | failure_reason | recoverable | quick_action | suggested_next |
|---|---|---|---|---|---|
| A1 | `status==401` | `auth_failed` | false | `fix_request` | 检查 `Authorization: Bearer <key>` 是否存在、是否带前缀、是否有多余空格；确认 key 与所用站点（国内站/国际站）一致 |
| A2 | `code` ∈ {`invalid_api_key`,`incorrect_api_key_error`,`invalid_authentication_error`,`InvalidApiKey`} | `auth_failed` | false | `fix_request` | 同上 |
| A3 | message ≈ `/Incorrect API key provided\|Invalid API-key provided\|Header 中未收到 Authentication/i` | `auth_failed` | false | `fix_request` | 同上 |
| A4 | `status==402` | `quota_exhausted` | false | `top_up_balance` | 账户余额不足，请充值后重试；充值到账可能有分钟级延迟 |
| A5 | `code` ∈ {`insufficient_quota`,`exceeded_current_quota_error`,`Arrearage`,`isv.OUT_OF_SERVICE`,`Throttling.AllocationQuota`} | `quota_exhausted` | false | `top_up_balance` | 账户余额/额度耗尽，充值或提额后恢复 |
| A6 | `code` 匹配 `/^1(113\|30[89]\|31[0-9])\|^1311$/`（智谱套餐/欠费类） | `quota_exhausted` | false | `top_up_balance` | GLM 套餐额度耗尽或账户欠费；充值或升级套餐 |

### 1.6.5 各上游错误体形状差异（**归因器必须适配**）

| 上游 | 错误体形状 | 与 OpenAI 标准差异 |
|---|---|---|
| OpenAI 标准 | `{"error":{"message","type","param","code"}}` | — [V][R1] |
| DeepSeek | 同 OpenAI 标准形状 | 无差异 [V][R3] |
| DashScope 兼容模式 | `{"error":{"message","type":"invalid_request_error","param":null,"code":"invalid_api_key"}}` | **完全一致**（已抓原文）[V][R7] |
| 智谱 GLM | `{"error":{"code":"1001","message":"..."}}` | **缺 `type` 与 `param`**；`code` 是字符串数字 [V][R9] |
| Kimi | `{"error":{"type":"content_filter","message":"..."}}` | **缺 `code` 与 `param`**（官方示例仅两个字段）[V][R5] |
| SiliconFlow | `{"code":20012,"message":"...","data":null}` | **完全没有 `error` 包裹层**，是自有形状 [V][R14] |
| OpenRouter | `{"error":{"code":<number>,"message":"...","metadata":{...}}}` | **`code` 是数字 HTTP 状态码**，不是字符串错误码；`type` 缺失，改用 `metadata.error_type` [V][R10] |

> **实现要求**：归因器的输入解析必须是「三路兼容」——(a) `body.error.{code,type,message,param}`、(b) `body.{code,message}`、(c) `body.error.code` 为数字时降级为 HTTP 状态码。**对外输出前必须补齐 `type`/`param`（`null`）**，否则违反 1.5.1 的 required 约束。

|---|---|---|---|

| OpenRouter（通用） | `429` 与 `503` **可能**带标准 `Retry-After`（秒）；OpenAI / Anthropic / Vercel / OpenRouter SDK 均已尊重该头 | 否 | [V][R10] |

| 阿里云百炼 | 错误码页与限流页**均未出现** `Retry-After` / `x-ratelimit-*`（已 grep 确认为 0 命中）；限流页只说明「通常在一分钟内恢复」 | 未文档化 | [V][R8][R16] |
| DeepSeek | 错误码页与限流页**均未出现** `Retry-After` / `x-ratelimit-*`（已 grep 确认为 0 命中） | 未文档化 | [V][R3][R4] |

| 智谱 GLM | 错误码页**未文档化响应头**；`1308`/`1310` 等的 message 内含 `next_flush_time`，可作为重置时间的**文本替代源** | 未文档化 | [V][R9] |

**归一化规则（实现直接照抄）**：
```
retry_after_seconds =
    parse_int(headers['retry-after'])                       // 优先
 ?? parse_int(headers['x-ratelimit-reset'])                  // 绝对时间戳时需 now 换算
 ?? extract_flush_time(error.message)                        // 智谱 "将在 ${next_flush_time} 重置"
 ?? (failure_reason == 'rate_limited' ? backoff.default : null)
```
若 `Retry-After` 为 HTTP-date 格式需按 RFC 7231 解析为秒差。[I]

## 1.8 模型名映射兼容性陷阱检查表

中转站做 `client_model → upstream_model` 映射时，**返回体里所有出现模型名的位置都必须回显客户端请求的原始名**。

| # | 字段/位置 | 陷阱 | 严重度 | 依据 |
|---|---|---|---|---|
| M1 | 响应体 `model` | 若回显上游真实模型名，暴露路由细节；部分客户端（成本统计、模型切换逻辑）会据此判断 | 高 | [V][R1] `model` 为 required |
| M2 | 流式**每个 chunk** 的 `model` | 必须整条流一致且与请求一致；有客户端在收到 chunk 时按 `model` 分桶 | 高 | [V][R1] |
| M3 | 响应 `id` | 必须带 `chatcmpl-` 前缀。有客户端/日志工具按前缀做类型判定 | 中 | [V][R1][R7] |
| M4 | `created` | 必须存在（required）且在一条流内恒定；不可用上游的旧时间戳导致客户端判定为过期 | 中 | [V][R1] |
| M5 | `system_fingerprint` | 可选但**不可凭空编造**；DashScope 恒返回 `null`。若映射后改变该值，会破坏部分客户端的 prompt-cache 命中判断 | 中 | [V][R1][R7] |
| M6 | `usage` 数值 | **必须与上游一致，不可重算**。重算会在 token 计费对账时暴露差异；`prompt_tokens_details` / `completion_tokens_details` 也应原样透传 | 高 | [V][R1] |
| M7 | `usage.prompt_tokens + completion_tokens != total_tokens` | 缓存命中场景下上游可能不满足加法关系，客户端若自行校验会误判 —— **同样不可"修正"** | 中 | [I] |
| M8 | `object` 字段 | 若上游给的 object 串不规范（如漏了 `.chunk`），客户端 JSON→类型映射会失败 | 中 | [V][R1] |
| M9 | `choices[].index`、`delta.tool_calls[].index` | 不可重排、不可重编号 | 高 | [V][R1] |
| M10 | `GET /v1/models` 的 `id` | 应对外暴露**中转站自己的模型名**（即客户端请求时使用的名字），`owned_by` 应统一且不泄露上游身份 | 中 | [V][R1] `id`/`owned_by` 为 required |
| M11 | 上游返回 `model` 与请求不一致 | 若上游擅自回显自己的模型名（如 `qwen3.8-max`），**必须在转发前覆写回客户端请求名** | 高 | [V][R7] 实测 DashScope 返回自有模型名 |
| M12 | 客户端会崩的字段缺失 | 上述 required 字段缺失时，openai-python/openai-node 走的是宽松 `construct_type`，**通常不崩**；真正会崩的是**强类型下游**（Vercel AI SDK 的 discriminated union、Go/Rust 严格解码器、`.strict()` 的 JSON Schema 校验） | 高 | [I] 基于 [V][R11][R13] 的宽松解析行为推断 |

> **M12 的实操结论**：不要指望「SDK 能容错」——中转站的对外契约必须按 1.2.2 的 required 集合**全部补齐**（哪怕是 `logprobs: null` 这种看似废字段），因为调用方可能是 SDK，也可能是严格的强类型解码器。

## 1.9 透传与改写边界清单

### 1.9.1 必须在字节层面保持不变（**RED LINE**）

| # | 内容 | 说明 |
|---|---|---|
| P1 | 成功响应体（HTTP 2xx）的**全部 JSON 字段与值** | 含 `usage` 的每一个数字 |
| P2 | 成功响应体的**字段顺序** | 部分客户端把 body 当字符串做 hash/缓存比对 |
| P3 | SSE 帧的**顺序**与**逐帧字节内容** | 特别是 `choices[].index`、`delta` 增量内容 |
| P4 | `data: [DONE]` 帧的存在与位置 | 少发会导致客户端 hang 到超时 |
| P5 | `finish_reason` 的取值 | 严禁把 `tool_calls` 归一成 `stop` 之类 |
| P6 | 流式 `usage` chunk 的出现时机与数值（若上游发出） | 见 1.3.3 |
| P7 | 成功响应的 HTTP 状态码 | 严禁"200 但内容里塞错误"的二次包装 |

### 1.9.2 允许增加的部分

| # | 内容 | 约束 |
|---|---|---|
| A1 | 响应头 | 但**不要新增与 CORS/缓存/内容协商冲突的头**；`Content-Length` 与压缩相关头必须在改 body 时重算 |
| A2 | 错误体 `error` 对象内部的新键 | 见 1.10 取舍 |
| A3 | 错误体顶层的非标准键（如 `relay_attribution`） | 见 1.10 取舍 |
| A4 | 仅在错误路径（非 2xx）改写/补齐 body | 成功响应一律不碰 |
| A5 | 仅在中转站自有端点（如 `/v1/models` 的 `owned_by`）表达路由信息 | 不进入上游响应体 |

### 1.9.3 必须合成的情况（上游没给合法错误体）

| 场景 | 处置 |
|---|---|
| 上游返回 HTML（如 504 网关页） | 合成 `{"error":{"message":"<截断后的原文，≤512 字符>","type":"server_error","param":null,"code":"upstream_gateway_error"}}`，状态码沿用上游 |
| 上游返回非 JSON 文本 | 同上，`code` 置 `null` |
| 上游连接失败（DNS/TCP/TLS） | 合成 502 + `code: "upstream_connection_failed"` |
| 本地超时 | 合成 504 + `code: "upstream_timeout"` |
| 智谱流式中途异常 | **不会返回错误码**，而是在 `finish_reason` 中给出异常原因 [V][R9] —— 归因器必须同时监听 `finish_reason` |

## 1.10 安全附加字段：命名与放置位置的取舍分析

需求书提到「非标准顶层字段如 `relay_attribution`」，并要求分析四种位置的取舍。

### 1.10.1 四个候选位置

| 位置 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| **① `error` 对象内** | `{"error":{...,"relay_attribution":{...}}}` | 与错误天然同生命周期；客户端解构 `error` 时顺手可得 | 部分严格客户端会用 JSON Schema / `additionalProperties:false` 校验 `error` 对象；OpenRouter 这类上游已在 `error` 内放了非标准 `metadata`，说明业界有先例 |
| **② 响应顶层** | `{"error":{...},"relay_attribution":{...}}` | **对官方 SDK 零风险**：两者都只解 `body.error`，顶层键完全不进入解析路径 [V][R11][R13] | 若有客户端严格校验顶层 schema 会失败；对非错误响应不适用 |
| **③ 响应头** | `x-relay-attribution: <base64 或紧凑 JSON>` | 完全不污染 body；**成功响应也能带**（headers 不在 body 字节比对范围内） | 头长度受限（建议 ≤4KB）；值需编码；CORS 下需 `Access-Control-Expose-Headers` 才能被浏览器读到 |
| **④ 可选开关 `?explain=1`** | 仅当带参数时注入 | 默认零侵入，最保守 | 客户端要改代码才能拿到；Agent 场景下"自动获得"的价值会打折扣 |

### 1.10.2 推荐方案（分层，可并行）

**默认行为（无需客户端改动）**：
```
错误路径（非 2xx）：
  body.error 内 —— 只放最小、最稳的一组，键名用短前缀避免与未来上游字段冲突：
    error.relay = {
      failure_reason: "rate_limited",
      recoverable: true,
      quick_action: "retry_with_backoff",
      suggested_next: "等待 12 秒后重试；建议同时降低并发",
      retry_after_ms: 12000,
      upstream: "deepseek"          // 上游标识，可选
    }
  顶层 —— 同时放一份，供需要完整上下文的客户端：
    relay_attribution = { ...同上, raw_error: "<上游原始错误体截断 ≤2KB>" }

成功路径（2xx）：
  响应头 —— x-relay-attribution: <紧凑 JSON 或 base64>
    （成功响应体一个字节都不能碰；头是唯一合规通道）
```

**键名推荐与理由**：

| 场景 | 推荐键名 | 理由 |
|---|---|---|
| `error` 内 | **`relay`**（而非 `relay_attribution`） | 短、不易与上游自有扩展（如 OpenRouter 的 `metadata`、GLM 的纯 `code/message`）碰撞 |
| 顶层 | **`relay_attribution`** | 顶层空间宽敞，用长名更自描述，且需求书已约定该名 |
| 响应头 | **`x-relay-attribution`** + 可选 **`x-relay-failure-reason`**（单值，便于 `curl -I` 排查） | 头名单值形式对运维最友好 |

**为什么同时放 `error` 内和顶层**：两者读的是不同人群。用官方 SDK 的用户拿 `err.error.relay`（SDK 已解包 `body.error`）；直接 `fetch` + `res.json()` 的用户拿 `body.relay_attribution`。**冗余成本是一次序列化，收益是零配置可用**。

**为什么不默认启用 `?explain=1`**：Agent 框架作者不会为了归因去改自己的 HTTP 层。默认开着、开关用于**关闭**（`?explain=0`）比默认关着更符合「零配置价值」定位。同时保留 `?explain=1` 作为强制开启语义（用于将来把默认调成关闭时的兼容路径）。

### 1.10.3 红线

1. **绝不**在成功响应体（2xx 的 JSON 或 SSE）里注入任何字段，包括 `relay_attribution`。
2. **绝不**为了塞归因而改变 `error` 对象的既有四个键的值。
3. 归因层抛异常时，必须**原样转发上游错误体**（fail-open）——宁可没有卡片，不可没有错误。
4. `raw_error` 截断，且**不得**包含用户 prompt 内容（上游 message 偶尔会回显输入片段，需要在截断前做一次遮蔽）。

## 2.2 状态码映射的取舍依据

`failure_reason` 必须映射到「SDK 会抛什么异常」，这一约束来自 openai-python/openai-node 的状态码 → 异常类分派表（1.5.3）。具体后果：

- **余额不足（`quota_exhausted`）不能返回 429**：429 会让 SDK 抛 `RateLimitError`，而多数 Agent 框架对 `RateLimitError` 有自动重试策略。余额不足是**不可重试**的，返回 429 会触发无效重试风暴。→ 推荐 **402**（SDK 落到 `APIStatusError` 基类，不触发任何自动重试；且 DeepSeek/OpenRouter/SiliconFlow 都用 402 表达余额问题，与上游语义一致）。
- **`content_filtered` 不能返回 429/503**：应返回 **400**，这样 SDK 抛 `BadRequestError`，框架不会重试。Kimi 与 DashScope 的原文都是 400。[V][R5][R8]
- **`upstream_overloaded` 应返回 503**：spec 在四个 POST 上显式声明 503 [V][R1]，且 5xx → `InternalServerError` 是各框架的通用重试信号。

# 第四部分 · 未核实事项

按「阻塞实现的程度」降序排列。

## 4.1 OpenAI 官方错误码页无法抓取（阻塞度：中）

- **现象**：`https://platform.openai.com/docs/guides/error-codes`、`/docs/api-reference/chat/streaming`、`https://developers.openai.com/api/docs/...` 全部返回 **HTTP 403 + Cloudflare 拦截页**（`Attention Required! | Cloudflare`）。`web_fetch` 工具与 `curl` 均被拦（同一出口 IP `240e:974:1e00:305::4b9`）。[U]
- **影响**：1.5.4 表中 `insufficient_quota`、`context_length_exceeded`、`invalid_request_error` 在 **OpenAI 侧**的确切 `type`/`code` 组合标为 `[I]`（行业通行推断），非原文核实。
- **补救**：用一个真实 OpenAI key 分别触发 401 / 429（限流）/ 429（配额）/ 400（超长）/ 404 各一次，落盘原始 body 后回填本表。这是**唯一**能把 `[I]` 升级为 `[V]` 的路径。
- **不阻塞的部分**：错误体的**形状**（`{"error":{message,type,param,code}}`）与 required 集合已由 R1 权威确认，无需该页。

## 4.2 火山方舟（Ark）错误与限流口径完全未核实（阻塞度：中）

- **现象**：`https://www.volcengine.com/docs/82379/1298454` 与 `https://docs.volcengine.com/docs/82379/1298454` 均返回 200 且约 790KB，但正文由 JS 客户端渲染，HTML 内**不含任何错误码内容**（对 `RateLimit` 命中 0 次，`429` 的 15 次命中全部落在 SVG 路径数据里）。`/sitemap.xml` 无有效 sitemap；`robots.txt` 只列 4 条 Disallow；部分文档 ID 会返回 SHA256 挑战页（`Please wait...`）。[U]
- **影响**：归因规则表中**缺少火山方舟组**。若 MVP 的上游清单包含方舟，则其错误必须走组 F 兜底（泛化归因），归因准确率会下降。
- **补救**：(a) 申请方舟测试账号，用真实请求触发各类错误并落盘；(b) 抓取其 Python/Go SDK 仓库中的异常定义；(c) 通过国内可访问的镜像/社区文档交叉核对后再标注 `[I]`。

## 4.3 OpenAI 是否在成功响应中返回 `x-ratelimit-*` 响应头（阻塞度：低）

- R1 的 spec 中没有任何 `x-ratelimit-*` 响应头声明；OpenRouter 明确声明**成功推理响应不带** `X-RateLimit-*`，只在自身限流的错误响应上带 [V][R10][R18]。
- **未核实**：OpenAI 本身是否在成功响应中返回这些头。历史上 OpenAI 曾返回 `x-ratelimit-remaining-requests` 等。
- **对实现的影响**：若要做「剩余额度」展示，不能依赖成功响应头；应改为 `GET /v1/models` 之外的独立额度查询（参照 Kimi 的 `/v1/users/me/balance` [V][R6] 与 OpenRouter 的 `GET /api/v1/key` [V][R18]）。这意味着**跨上游统一的余额查询接口在本期无法实现**，只能 per-upstream 适配。

## 4.4 「成功响应里的内容过滤」如何归因（阻塞度：低，但设计需定型）

- DashScope 用 `400 DataInspectionFailed` 表达拦截 [V][R8]，OpenRouter 用 403 + guardrail metadata [V][R10]，Kimi 用 `400 content_filter` [V][R5]——**都是错误路径**。
- 但 OpenAI 的 `finish_reason` 枚举里有 `content_filter`，且 `CreateChatCompletionResponse` 允许 200 + `finish_reason: "content_filter"` [V][R1]。这是**成功响应内的过滤信号**。
- **冲突**：红线 P1/P5 禁止改写成功响应体；但归因卡片又需要送达。
- **当前建议（待产品确认）**：仅通过响应头 `x-relay-attribution`（+ 可选的 `x-relay-failure-reason: content_filtered`）下发，**不碰 body**。这是一个需要产品拍板的设计选择，不是纯技术问题。
