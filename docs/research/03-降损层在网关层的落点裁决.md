# 传话层降损在中转站层的落点裁决

## 裁决速览表

| 模式 | 裁决 | 形态 | 一句话理由 | 落地模块名建议 |
|---|---|---|---|---|
| **P1 符号态提炼** | ❌ 不做 | 仅保留「只读 transcript」用于度量与审计，绝不改写回传 | 中转站流经的全是符号数据（JSON/文本），没有「原始载荷」可提炼；一旦改写成功响应，信任假设与按 token 计费同时受损 | `src/loss/transcript.ts`（只读，不参与出站组装） |
| **P2 调用前意图预检** | ✅ 做（分级） | 默认 `observe`；`enforce` 只对「高确定性 + 上游必拒」白名单规则；治理层异常/超预算无条件放行 | 错误路径优化，不砍成功路径收入；但 HTTP 层没有「模型下一轮自纠」，所以拦截必须又少又准又可绕过 | `src/loss/precheck/{index,rules.structure,rules.tools,rules.params,rules.schema}.ts` |
| **P3 失败归因** | ✅ 做（分层） | L0 原文透传 → L1 错误体 `error.metadata.relay` + `X-Relay-Attribution` 头 → L2 `?explain=1` 完整卡片；成功响应默认零注入 | 归因只出现在错误路径，不改变上游事实，信任成本最低而感知价值最高 | `src/loss/attribution/{index,rules.ts,card.ts}` |
| **P4 跨 turn 意图栈** | ❌ 不做 / ⚠️ 降级 | 用「请求内固有结构 + 有界窗口计数」做无状态指纹，只驱动低风险动作（文档推荐、控制台提示、额度提醒） | 意图栈需要 goal/subgoals 内容状态与跨副本一致性，直接破坏无状态管道；而「是不是 Agent」其实可由单请求自证 | `src/loss/fingerprint.ts` |
| **P5 执行轨迹可视化** | ⚠️ 降级做 | request-level trace：一次请求内的 auth→precheck→fingerprint→route→upstream→retry→classify→stream→meter 步骤记录 | 看不到用户的编排轨迹，但能看到**我们这一跳**的每一步；降损层自己引入的失败必须可定位 | `src/loss/trace.ts`（内存环 + 异常采样落库） |
| **P6 符号态缓存 / 归因记忆化** | ⚠️ 部分做 | 只缓存**纯函数**产物（编译后的规则表、正则对象、模型能力表），绝不缓存任何依赖运行时状态的判定结果 | 响应缓存命中 = 零收入 + 陈旧事故；但正则/规则编译是纯函数，缓存零风险 | `src/loss/attribution/rules.cache.ts`（有界 FIFO） |
| **P7 同轮只读调用去重** | ❌ 不做 / ⚠️ 降级 | 降级为「重复观测」：`duplicateInWindow` 计数并归因，不合并、不拦截、不返回缓存 | API 层没有「轮」的概念，替用户合并请求等于替用户做 Agent 框架的决策；但重复本身是极有价值的损耗信号 | `src/loss/dedup-observe.ts`（只读计数） |
| **P8 损耗量化基线** | ✅ 做（重点） | 无状态计数 + 固定桶直方图；明细抽样落 SQLite；指标命名对齐 OTel `gen_ai.*`；新增「降损层自身开销」与「代理量替代压缩率」 | 没有度量就没有下一步优化；且度量是本层唯一能自我证伪（overhead、误拦率）的机制 | `src/loss/meter/{index,metrics.ts,histogram.ts}` + `src/store/meter.repo.ts` |

**三条跨模式铁律（本次裁决新增，凌驾于单模式结论）**

1. **fail-open 在 HTTP 层的准确含义是「默认不拦、拦错可绕、异常必放」**，而不是「出错返回一个错误对象」——因为 HTTP 客户端没有「下一轮自纠」。
2. **改写 vs 附加**必须区分：禁止改写/删除/替换上游的既有字段与语义；默认不新增 relay 自有字段，仅 opt-in 附加；响应头通道永远优先于响应体通道。
3. **本层对外只承诺三件事**：错误更可读、更多畸形请求在第一跳就被挡住、你的 prompt 原文我们不落盘。禁止宣传「帮你省 30% token」（那是 P1 的承诺，本层不做）。

## 1. P2 预检：在「API 层」到底能检什么、不能检什么

### 1.0 结论先行

- **能检的边界 = 「请求体内自证的事实」+「本站在配置里权威掌握的注册表事实」**。两者都不需要触碰用户环境，也不需要对上游做任何探测。
- **不能检的边界 = 任何需要用户环境状态（DOM/文件系统/数据库/真实工具实现）或需要向上游/外部 URL 发起探测才能获得的事实**。
- **处置分级**：只有「高确定性 + 上游必然拒绝 + 本地即可权威判定」的规则允许 `reject`（返回 4xx）；其余一律 `observe`（记录 + 透传）；估算类规则一律 `warn`（永不阻断）。
- **fail-open 的正确落点**：治理层自身异常/超时/超预算 → 无条件透传；默认 tier 配置为 `observe`；`enforce` 只对白名单规则开放，且必须给客户端一个显式绕过开关。

### 1.1 可做规则穷举（附：确定性、上游是否也会拒、建议处置）

|---|---|---|---|---|---|---|

| R19 | 危险命令黑名单（对 `tool_calls[].arguments` 与 `tools[].function.parameters` 内的 shell 形态串做正则） | 本地正则 | 低（语义判断） | 否（上游不管） | info | **默认关闭**；开启也只 observe，仅 free 层做风控 |
| R20 | 请求体大小 / messages 数 / tools 数 / 嵌套深度超限 | 计数 | 确定 | 否（属资源保护） | block | reject(413/400) |
| R21 | 同一请求内重复/冲突的采样参数（同时给 `temperature` 与 `top_p` 极端值，或 `n>1` 与 `stream` 的已知不兼容组合） | 本地兼容表 | 低 | 视上游 | info | observe |

**四个必须写进实现约束的边界：**

1. **绝不执行用户提供的正则**。`tools[].function.parameters.pattern` 与 `dangerousCommandPatterns` 之外的任何用户正则，都可能触发 ReDoS，把「治理层 fail-open」变成「治理层阻塞主流程」。若确需校验 `pattern`，必须：限长（≤256）、限制回溯（预算内中断）、或只做「是否为合法正则」的编译检查而不实际匹配。
2. **JSON Schema 校验必须自研且只支持子集**（零运行时依赖，无 ajv）。支持 `type/required/enum/minimum/maximum/minLength/maxLength/items/properties/additionalProperties` 即可，且 `pattern` 按上一条处理。不支持的关键字要显式记录 `unsupported_keyword` 到 trace，避免「静默不校验」被误当作「校验通过」。
3. **预检必须有时延预算**（`LossReductionConfig.precheck.budgetUs`）。超预算即放弃并置 `PrecheckResult.degraded = true`，照常透传。
4. **模型能力表是本层最大的误判来源**：表过期 → 误拦。因此一切依赖能力表的规则（R13/R14/R15）默认只 `warn`，且能力表带版本号，`X-Relay-Rule-Version` 对外可见。

### 1.2 不可做规则穷举（以及为什么）

| 不可做 | 为什么网关看不到 |
|---|---|
| 「要点的 DOM 元素/选择器是否存在」（**P2 的原始场景**） | 网关没有用户的页面状态；这正是评估文档 §4 的结论，复核后仍成立 |
| 「文件路径是否存在」「命令是否有副作用」 | 网关没有用户的文件系统与进程 |
| 「这个 SQL 会不会删库」「这个金额是否合理」 | 需要业务语义与数据，网关只有 schema |
| 用户自定义工具的真实实现与其真实参数约束 | 网关只能按**模型声明的 schema**校验；schema 与实现是否一致，只有用户知道 |
| 「这个图片 URL 的内容是不是违规图片/是否真是图片」 | 需要真实抓取 → 把中转站变成 SSRF 引擎（见反方） |
| 「这个模型是否真的支持 tools/vision/json_schema」 | 只能靠本地配置表近似；配置必然滞后于上游 |
| 「这轮调用是否偏离了用户目标」（P4 范畴） | 无状态网关没有跨请求意图记忆 |
| 「上游配额/余额是否够」 | 只有上游（或本地额度账本）知道 |
| 精确 token 数 | 零依赖无 tokenizer；只能估算，估算值不可作为拦截依据 |
| 「客户端 SDK 会怎么解析这个响应」 | 不在请求里；只能按兼容假设设计（见第 2 节的 strict client 风险） |

### 1.3 误拦代价 vs 漏拦代价矩阵

定义：
- **误拦代价（False Positive Cost）** = 请求本来能成功，却被我们拦住。在 HTTP 层，这个代价是**非线性**的：客户端 SDK 抛异常 → Agent 流水线整任务失败 → 用户重跑 → 多消耗 token 与时间 → 并且用户归因于「这个中转站乱拦」。
- **漏拦代价（False Negative Cost）** = 打给上游后被上游拒。代价是**一次无效往返 + 可能的少量 token 费**，且落入 P3 可归因范围，客户端还能自纠。

| 规则类别 | 代表规则 | 判定确定性 | 上游也会拒 | 误拦代价 | 漏拦代价 | 处置 |
|---|---|---|---|---|---|---|
| A 结构硬错 | R1–R6、R8、R10、R16、R18(语法)、R20 | 极高 | 是 | 极低（拦对了几乎不可能误） | 低（一次往返） | **reject** |
| B 语义闭包 | R7、R11 | 高 | 是（通常） | 低（个别框架会自己补历史） | 低 | **observe 起步，证据足够后升 reject** |
| C 参数边界 | R9(上限)、R13、R14、R17 | 中（依赖 provider/模型表） | 多数是 | **高**（不同上游边界不同，例如 `temperature` 上限在 OpenAI 兼容面是 2，但部分非 OpenAI 系上游只接受 1；用一套边界去拦所有上游 = 必误拦） | 中 | **observe** |
| D 估算类 | R15 | 低 | 是 | **极高**（少算几百 token 就拦住一条正常长上下文请求） | 中 | **warn，永不 block** |
| E 风控/语义 | R19 | 低 | 否 | **极高**（讨论 `rm -rf` 的文章、教学 prompt 会被误伤） | 极低（上游不拒，用户自己承担） | **默认 off；开启只 info/observe** |

**矩阵结论**：可 reject 的只有 A 类。把 C/D/E 类也设成 reject，是把「降损」做成「自我 DDoS」。

**量化验收口径（建议写进测试）**：A 类规则的误拦率必须为 0（用历史成功请求回放验证）；B 类上线后 2 周内若误拦率 > 0.1%，自动降级为 observe。误拦的判定信号见 1.5。

### 1.4 fail-open 在 HTTP 层意味着什么（200 透传还是 400 拦截？）

这是本次研究最重要的一点修正：**P2 在工具层的 fail-open 语义不可直接搬到 HTTP 层。**

- 工具层的 fail-open = 「返回一个 tool-error 结果而不是硬中止」——因为模型还在 loop 里，**下一轮能自纠**。
- HTTP 层的客户端是**一次性的调用者**：它没有「下一轮」的保证。返回 400 就是让 SDK 抛异常；很多 Agent 框架（LangChain/LlamaIndex/Dify 的默认错误处理）在 chat completion 抛异常时直接终止整条任务链。**所以 HTTP 层的 fail-open 必须理解为「默认不拦」，而不是「拦住但返回一个可读的错误」。**

准确语义拆成三条：

1. **异常即放行**：预检自身抛错、超时、超预算、内存/CPU 异常 → 完全按原请求透传，并记 `precheckDegraded`。治理层永不成为主流程的单点（SKILL.md 安全原则第 5 条）。
2. **默认不拦**：默认 tier（含 standard）为 `observe`；只有 `enforce` 且命中 A 类规则才拦。
3. **拦截必须可绕过**：见 1.5。

**那到底 200 还是 400？——分阶段裁决（按「是否已把请求体交给上游」划界）**

| 阶段 | 场景 | 处置 | 依据 |
|---|---|---|---|
| 阶段 A | 本层在**发起上游请求之前**判定请求不可处理 | **4xx**（400 结构/参数、404 模型不存在、413 过大） | 与 OpenAI 兼容生态一致：上游自己也是 4xx（DeepSeek 400 Invalid Format / 422 Invalid Parameters）；SDK 以 status 判定错误与重试，返回 200 会破坏 SDK 契约并让客户端解析 `choices` 失败 |
| 阶段 B | 上游已应答（非流式） | **透传上游 status** + 归一化错误体（P3 附加） | 事实来自上游，中转站无权改判 |
| 阶段 C | 上游已 200 且流已开始，中途出错 | **HTTP 200 无法改** → 在 SSE 里注入 `error` 帧 + `finish_reason: "error"` 终止流 | OpenRouter 的做法：请求一旦开始生成，HTTP status 保持 200，错误放在 body/SSE data 里；这是业界已验证的语义 |

**反方（主张「一律 200 透传」）**：有观点认为 HTTP 层应该永远 200，把一切都放进 body，避免任何「网关改判」。反驳：请求前校验失败返回 200 会让 OpenAI SDK、以及所有以 status 判定重试的客户端**无法区分**「成功但内容为空」和「输入非法」，比 4xx 更糟。所以正确的分界不是「是否加工」，而是**「判定点在上游之前还是之后」**：上游之前用 4xx，上游之后保留上游 status，只有「已提交且无法再改 status」的流中错误才退化为 200+error。

### 1.5 拦错了，怎么让客户端可恢复

拦截的信任成本 = 误拦概率 × 恢复难度。把恢复难度压到零，是让 P2 能被接受的前提。

**四层恢复机制：**

1. **错误体自描述、可机器修复**（OpenAI 兼容形状 + 扩展位）：
   ```json
   {
     "error": {
       "message": "relay precheck: tool_call_id 'call_abc' has no matching assistant.tool_calls entry",
       "type": "invalid_request_error",
       "param": "/messages/3/tool_call_id",
       "code": "relay_precheck_failed",
       "metadata": {
         "relay": {
           "rule": "orphan_tool_call_id",
           "rule_version": "p2-3",
           "pointer": "/messages/3/tool_call_id",
           "fix": "remove this tool message or add the missing assistant.tool_calls entry",
           "bypass": "X-Relay-Precheck: off"
         }
       }
     }
   }
   ```
   `param` 用 JSON Pointer，客户端可以**程序化定位并自动改**。
2. **显式绕过开关**（误拦永远可自救）：
   - 单请求：`X-Relay-Precheck: off`（或 `?precheck=off`）；
   - key 级：控制台/`PATCH /admin/keys/{id}` 永久关闭；
   - 响应头回显生效状态：`X-Relay-Precheck: enforced|observed|off`。
3. **误拦自证 + 规则自动降级**：被拦请求（含 `payloadHash` 与 `rule`）进入短窗口表；若同一 key 在 60s 内以绕过开关重发同一 `payloadHash` 且**成功**，判定该次拦截为 false positive → 该规则对该 key（或全局，可配）在冷却期内自动降级为 `observe`，并计入指标 `relay.precheck.false_positive`。这是**把「误拦」变成一个可观测、可自愈的数据**，而不是一场客服事故。
4. **被拦请求不计费**：预检拦截不消耗上游 token，决不能出现在计费账单里（否则「拦了还收钱」会摧毁信任）。

**反方**：绕过开关会被滥用（客户端一律带 `off`，P2 形同虚设）。反驳与缓解：绕过是**客户端对自己请求负责**的显式声明，且 `off` 只关闭「本层语义校验」，不关闭风控与限速；同时把「是否绕过」做成指标——如果某 key 绕过率 > 50%，说明我们的规则对该客户是净负担，应当默认给他 `off`（而不是继续骚扰他）。

### 1.6 反方意见汇总（第 1 节）

- **反方 1：P2 纯属多此一举，上游本来就会拒。** 部分成立。A 类规则的价值不是「避免错误」，而是**省一次往返、把不可读的上游报错变成可读定位**（上游 400 经常只说「Invalid request body format」）。价值量级是个位数百分比的请求数，别夸大。
- **反方 2：图片 URL 可达性检查应该做（OpenRouter 就做，见 `image_download_failed`）。** 这是本次最实质的反方。OpenRouter 确实把「图片下载失败」做成了错误类型，说明可达性检查在产品上是成立的。但**我方裁决仍为「默认关闭、opt-in」**，理由：①可达性检查要求中转站主动向**用户提供的任意 URL** 发请求，这是教科书级 SSRF 面（需 IP 黑名单/禁跳转/禁内网/超时/小响应体上限，见 OWASP SSRF Cheat Sheet）；②我方是零依赖自研、单机部署，做这件事的安全审计成本远高于 OpenRouter 这样的专职团队；③收益（少一次往返）远小于风险（成为内网探测跳板）。**折中方案**：只做 URL 语法校验（R18，永远开）＋ 可选「HEAD 探测」开关（默认关，仅允许 http(s)、禁 3xx 跳转、禁私网段、超时 1.5s、不读 body）。
- **反方 3：`observe` 只记不拦等于没做。** 反驳：`observe` 是**规则毕业流程**（先积累误拦/漏拦证据，再升级 reject），这条路径本身就是 P8 度量驱动优化的实例；且对 standard 层客户，`observe` 也有价值（响应头回显 + 指标对我们的路由与文档优化）。

**第 1 节裁决**：P2 做，形态为「默认 observe + A 类白名单 enforce + 三阶段 fail-open + 四层恢复机制」；`enforce` 规则清单与 rule_version 必须版本化并可对外查询。

## 2. P3 失败归因：不破坏「我只是管道」的交付通道

### 2.0 结论先行

- 推荐：**响应头优先（`X-Relay-Attribution-*`）＋ 错误体扩展位（`error.metadata.relay`）作为默认**；`?explain=1` / `X-Relay-Explain: 1` 解锁完整卡片（含 evidence、候选上游、重试轨迹）。
- **不改写上游错误原文**：`error.message` 保留原文，建议另置字段；若必须内联，只允许**在末尾追加**一句 ≤80 字的建议，不删除、不改写、不替换。
- **成功响应默认零注入**；若未来要附加 relay 字段，也只是 opt-in，且必须明确「附加 ≠ 改写」。
- 流式是硬约束：**响应头只能在第一字节前决定**，所以归因必须在上游响应头到达时给出「初判」，中途细化只能走 SSE 帧。

### 2.1 四通道比较

| 维度 | (a) 改写 error 对象加字段 | (b) 顶层 `relay_attribution` | (c) 响应头 `X-Relay-Attribution-*` | (d) 显式开关 `?explain=1` / header |
|---|---|---|---|---|
| 兼容性风险 | **低**：OpenAI 的 Error schema 只定义 `type/message/param/code`，SDK 解析宽容；业界先例明确（OpenRouter 的 `error.metadata`） | **中高**：顶层新增键会被 strict 客户端（Pydantic/zod `.strict()`）拒绝；且与「兼容体」的契约感冲突 | **极低**：不碰 body | 低（显式请求=明确同意） |
| 可发现性 | 中：客户端必须去看错误体 | 中 | 低：多数 SDK 默认不暴露 headers，需要显式读取；浏览器场景还需 `Access-Control-Expose-Headers` | **高**：文档一句话即可教会 |
| 可携带信息量 | 中：可放结构化 JSON（`{failure_reason, recoverable, suggested_next}`） | 高：任意结构 | **低**：单行 ASCII、长度受代理/HTTP2 头限制；中文要 URL-encode，可读性差 | 高：完整卡片、evidence 数组 |
| 流式可用性 | 仅 pre-stream 错误可用；mid-stream 只能走 SSE 帧 | 同左 | **仅 pre-stream 可用**（首字节前）；流中无法加头 | 同左（开关在请求侧，交付仍受阶段限制） |
| 实现代价 | 低（改错误体构造） | 低 | 低 | 低（解析 header/query + 分支） |
| 信任风险 | 低（错误路径本来就是坏消息） | 低 | 最低 | 最低 |
| 中间层剥离风险 | 无 | 无 | **有**（部分反向代理/CDN 会丢弃自定义头） | 无 |

### 2.2 推荐方案（分层 + 降级链）

**通道分层：**

| 层 | 触发条件 | 交付内容 | 通道 |
|---|---|---|---|
| **L0 保底** | 永远 | 上游 status（透传）、上游 `error` 原文（一字不改）、`Retry-After`（透传上游；上游没给而我们能算出退避时合成，见 RFC 9110 §10.2.3 允许 `delay-seconds` 或 HTTP-date） | body + 头 |
| **L1 默认**（standard/pro，可 key 级关） | 归因成功且置信度 ≥ 阈值 | `error.metadata.relay = {failure_reason, recoverable, suggested_next:{action, retry_after_ms}, upstream, confidence}`；同时 `X-Relay-Attribution: <compact>`（如 `rate_limited;retry_with_backoff;retry_after=42;conf=0.9;rule=p3-7`） | (a)+(c) |
| **L2 深度**（`?explain=1` 或 `X-Relay-Explain: 1`，或 pro 层默认） | 客户端显式要求 | 上面的全部 + `evidence[]`（脱敏后的上游线索）+ `attempts[]`（本层重试/切换上游轨迹）+ `rule_version` | (a)+(b 可选)+(c)+(d) |

**为什么以「错误体 (a) + 响应头 (c)」为默认，而不是顶层 (b)**：错误体是**唯一保证客户端一定会读到的位置**（SDK 抛异常时会把 `error.message` 打出来），响应头是**唯一保证不污染 body 的位置**。两者并集覆盖了「人读」和「机器读」。顶层字段 (b) 收益与 (a) 重叠，却带来 strict client 风险，因此只在 L2 作为可选附加。

**降级链（任何一环失败都退回更保底的层）：**

1. 归因器异常 / 超出时延预算 → L0，并记 `attribution.degraded`。
2. 上游响应体不是 JSON（HTML 网关页）→ 跳过 `error.metadata` 注入，只走响应头；若 body 可安全当文本处理，则只在**我们自己的** message 包装里给建议，绝不替换原文。
3. 响应体已开始流式 → 只剩 SSE 帧：`data: {"error":{...,"metadata":{"relay":{...}}},"choices":[{"delta":{"content":""},"finish_reason":"error"}]}`（OpenRouter 已验证的形态：错误出现在顶层，`choices` 带 `finish_reason:"error"` 用于正确终止流，HTTP status 保持 200）。
4. 客户端声明 strict 模式（`X-Relay-Attribution-Mode: header-only`）→ 只走 (c)。
5. 头部通道被中间层剥离（检测不到我们自己的头也正常，无法检测被剥离）→ 因此默认同时开 (a)，不要单靠头。

**必须做的脱敏（与第 4/6 节交叉）**：上游错误文本经常回显用户内容（内容过滤错误会带被拦片段，OpenRouter 的 moderation metadata 就把 `flagged_input` 截断到 100 字符）。因此 `evidence[]` 进入响应与 trace 前必须经过**截断（≤120 字符）+ 敏感模式遮蔽（sk-、AKIA、Bearer、邮箱、手机号、身份证）**，且默认不返回（`includeEvidence: false`）。

### 2.3 为什么不能改写成功响应

**四条正面理由：**

1. **信任假设**：成功路径是「我只转发」的合同本身。错误路径上「加一句解释」不改变事实（错误本来就是上游的坏消息）；成功路径上任何改动都可能改变用户拿到的结果。
2. **有损事故面**：评估文档 §2.2 劣势 2 的结论复核后仍成立——一个提炼/注入 bug 就是客户事故，而纯管道永远不会有这类事故。
3. **对账与复现**：成功响应的 `usage`、`model`、`choices` 是计费依据与复现依据；注入字段会改变字节数与哈希，使「可验证透传」失去基准（第 6 节的可验证机制依赖字节一致性）。
4. **生态兼容**：JSON mode / strict schema 客户端、把响应原样入库的用户，都会被未知字段污染。P1 的真实对象是「环境原始载荷」，在中转站不存在（评估文档 §4 复核成立）。

**反方（本次研究必须诚实呈现）**：OpenRouter 在**成功响应**上确实附加了自有字段——`native_finish_reason`（上游原始 finish_reason）、`provider`、`usage.cost`，并通过 `X-OpenRouter-Metadata: enabled` 在成功响应上返回完整的 `openrouter_metadata`（路由策略、候选端点、pipeline 阶段）。这说明「成功响应附加字段」在生态里是被接受的，且用户愿意为可观测性埋单。

**因此本节的准确裁决是「区分改写与附加」：**

- **禁止**：改写、删除、替换成功响应的任何既有字段与语义；改变 `choices`/`message.content`/`usage` 的既有值。
- **默认不做**：新增 relay 自有字段。
- **允许（opt-in）**：在客户端显式要求时，向成功响应附加 relay 自有命名空间下的字段（例如 `relay.trace_id`、`relay.route`）；一旦开启，必须在文档里说明「这是附加字段，不改变任何既有字段」，并给 strict 客户端提供 `header-only` 模式。
- **始终允许**：成功响应上加 `X-Relay-*` 响应头（零语义侵入），例如 `X-Relay-Mode`、`X-Relay-Trace-Id`、`X-Relay-Rule-Version`。注意浏览器场景需 `Access-Control-Expose-Headers: X-Relay-Trace-Id, ...`，否则前端读不到。

### 2.4 反方意见汇总（第 2 节）

- **反方 1：响应头通道没用，SDK 不读 header。** 部分成立（OpenAI SDK 不把自定义头映射到对象上），所以 (c) 只作为 (a) 的冗余而非主力；但它的价值在 `curl`/网关日志/排障与「流式中无法注入 body」时的唯一手段。
- **反方 2：中文归因卡片会引入编码与长度问题。** 成立。`X-Relay-Attribution` 只放 ASCII 机器码（`failure_reason`/`action`/数字），人话解释放 body；中文只出现在 L2 的 body 字段。
- **反方 3：改 `error.message` 会破坏用户既有日志正则。** 这是我把「原文保留 + 建议另置字段」定为默认的直接原因。若产品坚持内联，只能追加，且提供 `X-Relay-Original-Message-Hash` 供比对。
- **反方 4：归因可能误导（把上游 500 猜成限流）。** 成立。因此 `AttributionCard.confidence` 必须对外可见，且 `failure_reason` 的取值域收敛为 `types.ts` 中已冻结的枚举；低置信度时降级到 `unknown` 而不是硬猜。

**第 2 节裁决**：P3 做，形态为「L0/L1/L2 三层 + (a)+(c) 默认 + (d) 解锁深度 + 五级降级链 + evidence 默认关闭」；成功响应「禁止改写、默认不附加、允许 opt-in 附加与响应头」。

## 3. P8：中转站应该量什么

### 3.0 命名规范（先定名字，再定指标）

- 直接采用 **OpenTelemetry GenAI 语义约定**的命名与单位，避免与生态分叉：
  - `gen_ai.client.token.usage`（Histogram，单位 `{token}`，属性 `gen_ai.token.type = input|output`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.response.model`）；
  - `gen_ai.client.operation.duration`（Histogram，单位 `s`，错误时带 `error.type`）；
  - `gen_ai.client.operation.time_to_first_chunk`（Histogram，单位 `s`，仅流式）与 `gen_ai.server.time_to_first_token`（服务端视角首 token）。
  - 已知晓：GenAI semconv 已从 opentelemetry.io 迁移到独立仓库，且状态为 **Development**；因此我方**锁定版本并允许本地扩展**，不假设其稳定。
- 本层自有指标统一前缀 **`relay.`**（不与 `gen_ai.*` 冲突）。
- 桶边界直接抄规范给的建议边界（延迟用 `[0.01, 0.02, 0.04, ..., 81.92]` 秒；token 用 `[1, 4, 16, ..., 67108864]`），这样直方图可近似分位且不需要存全量样本。

### 3.1 指标清单（口径 / 单位 / 为什么能指导下一步优化）

| # | 指标（建议名） | 类型·单位 | 计算口径 | 采集态 | 能指导什么 |
|---|---|---|---|---|---|
| M1 | `relay.requests.total` | Counter `{request}` | 每个进入网关的 HTTP 请求 +1；维度 `tier/keyId/model/provider/outcome(http_status)`；`outcome ∈ success/client_error/upstream_error/relay_error/aborted` | **无状态** | 分母。`relay_error` 是唯一「必须永远为 0」的指标；`aborted` 单独看，避免客户端取消污染错误率 |
| M2 | `relay.upstream.errors` | Counter `{error}` | **双写**：原始 `upstream_status` + 归一化 `failure_reason`。保留 raw 是因为归一化会丢信息（同为 429，可能是 RPM 限流也可能是配额耗尽） | **无状态** | 识别坏渠道（某 provider 429 占比畸高）→ 调权重/摘除；识别模型级问题 → 换路由 |
| M3 | `relay.attribution.hits` | Counter `{error}` | 每个进入归因器的错误 +1；维度 `failure_reason/quick_action/confidence_bucket/rule_id`；另设 `relay.attribution.unclassified` | **无状态** | **`unclassified` 占比就是 P3 的下一个 TODO 清单**：规则表有洞时它升高；配合样本沉淀（第 4 节 trace）做规则迭代 |
| M4 | `relay.errors.recoverable.ratio` | Gauge（由计数推导） | `Σ recoverable / Σ errors`；`recoverable` 由规则表给出布尔 | 无状态计数→离线算比例 | 决定自动重试策略的覆盖面；也告诉销售「我们能救回多少失败」 |
| M5 | `relay.retries.duplicate` | Counter `{request}` | `(keyId, payloadHash, model)` 在滑动窗口 W（默认 60s）内第 2 次及以后的出现次数；落到 `MeterRecord.duplicateInWindow` | **无状态**（有界 TTL 计数表） | 直接量化「客户端在自己瞎重试」的浪费。**必须声明口径**：单副本内计数，多副本会低估；跨副本需按 key 分片或落库去重（`requestId` 唯一约束 + `INSERT OR IGNORE`） |
| M6 | `gen_ai.client.operation.time_to_first_chunk` 与 `relay.request.duration` | Histogram `s` | TTFB = 上游首字节 − 发起上游连接时刻（**不含**本层排队/预检）；总延迟 = 响应末字节 − 收到请求首字节。分位从固定桶近似 | **无状态** | 区分「上游慢」与「我们慢」：TTFB 正常但总延迟长 → 输出长/上游吐字慢；overhead 占比高 → 降损层拖慢了 |
| M7 | `gen_ai.client.token.usage` | Histogram `{token}` | 优先用上游 `usage`；缺失时不报（**不用估算充数**，会污染口径） | **无状态** | 成本与用量基线；与 M8 联合判断输入是否可缓存 |
| M8 | `relay.prompt_cache.hit_ratio` | Gauge | `Σ cached_prompt_tokens / Σ prompt_tokens`；来源：OpenAI 系 `usage.prompt_tokens_details.cached_tokens`、DeepSeek `usage.prompt_cache_hit_tokens`（对应 `prompt_cache_miss_tokens`）；缺失的请求**不进分母** | **无状态** | **本层最重要的一条「不改内容就能降本」路径**：缓存命中率低 → 建议客户端稳定前缀、使用 `prompt_cache_key`。上游成本下降、我们毛利上升，而用户按 token 的付费口径不变——这条正好补上了评估文档「降损=自砍收入」结论的缺口 |
| M9 | `relay.cost.total` / `relay.cost.per_mtok` | Counter（**micro-CNY 整数**）/ Gauge | `cost = (uncached_in×in_price + cached_in×cached_price + out×out_price)/1e6`；未配置价格的上游计入 `relay.cost.unknown`（**不得默认 0**） | **无状态** | 找亏损模型/渠道 → 调路由权重；发现某客户集中在最贵模型 → 引导；也是 Pro 定价的真实依据 |
| M10 | `relay.overhead.duration` + `relay.overhead.ratio` | Histogram `s`（µs 精度）+ Gauge | 每阶段 `monotonicUs` 差值：`precheck/classify/fingerprint/meter/trace`；ratio = overhead / total | **无状态** | **硬门槛**：precheck p99 > 2ms 或 ratio > 3% 就必须自动降级为 observe/off。这是「治理层不得成为单点」的量化证据，也是对外可信度的公开指标 |
| M11 | `relay.precheck.violations` / `relay.precheck.blocked` / `relay.precheck.false_positive` | Counter | 违规命中数（按 `rule_id/severity`）、实际拦截数、误拦自证数（1.5 节机制） | **无状态** | 规则毕业/退休的判据：某规则长期零命中 → 删；某规则误拦率 > 阈值 → 自动降 observe |
| M12 | `relay.reduction.*`（**P1 压缩率的替代物**） | Counter | 见 3.2 | 无状态计数 + 离线推导 | 把「降损收益」变成可比数字，且在无法度量真实轮次时明确标为代理量 |
| M13 | `relay.trace.stage.failures` | Counter | 按 `failedAtStage` 计数（auth/precheck/route/upstream_request/upstream_response/classify/stream） | 无状态 | 「哪一步最常坏」的直方图；比错误码分布更接近根因 |

### 3.2 符号态压缩率的替代物（本层不适用时的口径）

P1 的原始指标是「原始载荷 vs 符号态体积」。中转站流经的全是符号数据，**该指标在本层不存在对象**。替代物必须是**可诚实辩护的代理量（proxy metric）**：

| 替代指标 | 口径 | 局限（必须写进文档，禁止对外夸大） |
|---|---|---|
| `relay.reduction.avoided_bytes` | 被预检拦截的请求体字节数之和 | 只代表「没打给上游的字节」，不代表省了 token |
| `relay.reduction.wasted_tokens` | 上游已返回 `usage` 但 `outcome != success` 的 token 数之和 | 是「失败调用花掉的钱」的精确度量，但不等价于「模型重推的浪费」 |
| `relay.reduction.recovered_requests` | 本层自动重试/切换上游后成功的请求数 | 直接对应「把失败变成功」，是最硬的一条收益 |
| `relay.reduction.duplicate_requests` | 60s 窗口内重复请求数（= M5） | 只能近似「被浪费的重推轮次」；跨副本会低估 |
| `relay.reduction.prompt_cache_saved_tokens` | `cached_prompt_tokens × (in_price − cached_price)` | 是真实成本节省，但归因于上游能力与用户行为，**不是我们改写的功劳** |

**对外话术纪律**：可以承诺「减少无效往返」「把失败讲清楚」；**不可以**承诺「帮你省 30–50% token」——那是 P1 的承诺（本层不做），且评估文档 §9 的 Pro 定价正是建立在这个高估之上（见附录 C）。

### 3.3 必须无状态 vs 可以离线聚合（这条边界决定架构）

**必须无状态（请求路径内、O(1)、进程内累加）：**
- 所有 Counter 与固定桶直方图（M1、M2、M3、M5、M6、M7、M9、M10、M11、M13）；
- 短窗口重复检测表（有界 + TTL，容量上限必须显式配置，否则就是内存泄漏）；
- 并发计数（用于限流与指纹特征）。

**可以离线聚合（批处理 SQLite / 导出 JSONL）：**
- 分位（从桶近似，或对抽样明细算精确分位）；
- 按 key/tenant/model/provider 的日报周报与成本对账；
- 归因规则命中率与漏判复盘（需要看 `unclassified` 的原文样本）；
- 规则版本 A/B（`rule_version` 维度）；
- 误拦申诉率与延迟趋势。

**必须落明细（不能只留聚合）：**
- 被拦截请求的 `payloadHash + rule_id + pointer`（误拦复盘需要）；
- 上游错误原文的**哈希 + 长度 + 脱敏后摘要**（规则迭代需要，正文不留）；
- trace 的**异常采样**（第 4 节）。

**卡片性与标签纪律**：`keyId`、`payloadHash`、`requestId` 这类高基数维度**不得**进指标标签（会打爆直方图基数），只进 SQLite 行；指标维度只保留 `tier/model/provider/outcome/failure_reason/rule_id` 这种低基数集合。

### 3.4 反方意见汇总（第 3 节）

- **反方 1：度量是内部的事，与「我只是管道」无关，为什么要在研究里花最大篇幅？** 反驳：度量是**唯一能让本层自证清白或自我否定的机制**。没有 overhead 指标，「不拖慢主流程」是口号；没有误拦率指标，「fail-open」是口号；没有 unclassified 指标，「失败归因」会停在第一版规则表上腐烂。
- **反方 2：SQLite 扛不住度量写入。** 部分成立。因此设计为「进程内计数 + 定时批量 flush + 只对异常/抽样落明细」，并且**数据库故障必须降级为内存**（`src/store/index.ts` 已冻结该约束），网关主路径不依赖 DB。
- **反方 3：OTel GenAI semconv 还是 Development，绑定它是否过早？** 采纳其**命名与单位**（避免自造术语），但不采纳其 SDK 依赖（零依赖约束）；本地保留 `relay.*` 扩展位，未来迁移只改导出层。
- **反方 4：`wasted_tokens` 这样的指标会诱导我们把失败做大以显得收益高。** 这是真实的目标错位风险，因此该指标**只做内部基线**，不进对外 SLA/宣传；对外只讲 `recovered_requests`。

**第 3 节裁决**：P8 做，且是本层的**第一优先级**（先于 P2/P3 的规则完善）；形态为「OTel 命名 + 无状态计数/直方图 + 明细抽样 + SQLite 离线聚合 + 高基数维度不入标签」。

## 4. P5 降级形态：request-level trace

### 4.0 结论先行

- **原形态（多步编排轨迹可视化）确实做不了**：中转站看不到用户 Agent 的编排，能看到的最长单位是一次 HTTP 请求。评估文档 §3.4 的结论**成立**。
- **但「做不了」不成立的是它的推论「所以不做」**。降级形态 request-level trace 是可做的，而且**对本层是刚需**：降损层是唯一一个「在用户流量路径上额外做事」的组件，它自己引入的失败必须能被定位，否则违反 SKILL.md「治理层不得是黑盒」的原则。
- 形态 = `TraceRecord`（`src/core/types.ts` 已冻结）：一次请求内 `auth→precheck→fingerprint→route→upstream_request→upstream_response→retry→classify→stream→meter→respond` 的步骤序列 + `offsetMs` + `failedAtStage`。
- **可选增强（不存会话内容）**：用客户端提供的关联键（`X-Relay-Session-Id` / `X-Relay-Session-Path`，借鉴 Helicone Sessions 的 `Helicone-Session-Id`+`Helicone-Session-Path` 设计）把 N 条 request trace 串成一条「会话线」。**关联键由客户端提供，我们只做分组，不推断、不存正文**——这样既得到"轨迹"的运营价值，又不引入 P4 的有状态架构与内容风险。

### 4.1 设计

```
TraceRecord {
  traceId, requestId, startedAt, durationMs, outcome,
  failedAtStage?, 
  steps: TraceStep[]        // 上限 maxSteps，超出则合并/截断
}
TraceStep { stage, at, offsetMs, ok, summary, detail?, error? }
```

- **存储策略**：内存环（`ringSize`，默认 512–1024，O(1) 写入）+ 仅对 `outcome != success` 或 `overhead` 超阈值的 traces 落库（避免写放大）；`persist=false` 时纯内存。
- **脱敏**：`summary`/`detail`/`error` 一律**不得内联正文**；上游错误文本先截断 + 遮蔽（第 2.2 节）。`detail` 只允许 `string|number|boolean` 的低基数键值（与 `TraceStep.detail` 的类型一致）。
- **对外**：`X-Relay-Trace-Id` 出现在每个响应（含成功）；Pro 层提供 `GET /v1/relay/traces/{traceId}` 自助查询（只回元数据）。
- **采样**：默认只留异常；`trace.sampleRate` 可配置，正常请求按比例留样用于基线。

### 4.2 对运营/排障的真实价值（为什么不是「聊胜于无」）

1. **故障定位从「猜」到「看」**：一次失败的完整因果链——是鉴权失败、预检误拦、路由选到坏上游、上游 TTFB 超时、流中途断、还是归因器自己崩了。这张表把「错误码」升级成「阶段」。
2. **误拦申诉的仲裁证据**（与 1.5 节联动）：用户报「你拦错了」，凭 `traceId` 一秒定位到 `rule_id` 与 JSON Pointer。
3. **规则回归的测试夹具来源**：异常 trace 集合就是 P2/P3 的 case 库；每次改规则用真实失败样本回放（这是「先度量后优化」的落地形态）。
4. **容量与成本决策**：`relay.trace.stage.failures` 直方图告诉团队「下一步该修哪一步」，以及哪一步的耗时在增长。
5. **跨请求的运营视图（opt-in）**：客户端带 session 键后，可看到「一次会话里第 3 次请求开始失败」「会话内重复请求率高」——这是**运营/客服视角**的轨迹，与 P5 原形态（给终端用户看的可视化编排）不同，但价值真实。

### 4.3 反方意见汇总（第 4 节）

- **反方 1（最强）：trace 本身就是数据，是隐私风险的载体。** 成立且严重。上游错误文本常含用户内容片段（内容过滤尤其如此）。因此裁决里**强制**：trace 的文本字段必须脱敏 + 截断，禁止原文入库，且 trace 的保留期不得长于明细保留期。
- **反方 2：单请求 trace 对普通 API 用户只是「更好的日志」，包装成 P5 是虚假宣传。** 成立。**禁止**在对外文案里说「轨迹可视化/编排可视化」；只能说「请求级追踪（per-request trace）」。
- **反方 3：流式请求的 trace 只有流结束才完整**，实时排障看到半条。成立，无法根治（除非在流中增量落盘，成本高）；缓解：流中断时把已记录步骤立即落盘（`failedAtStage='stream'`）。
- **反方 4：session 键会把「串意图」风险带回来。** 只在「客户端显式提供键 + 我们只做分组统计、不做内容拼接、不出现在任何响应语义字段」三条同时满足时风险可控；一旦用于「记住某会话上一轮说了什么」，就退化为 P4，禁止。

**第 4 节裁决**：P5 原形态不做；request-level trace 做（含内存环 + 异常落库 + 脱敏 + `X-Relay-Trace-Id`）；客户端 session 键串联为 opt-in 增强。

## 5. P4-lite：只基于请求特征的无状态指纹

### 5.0 结论先行

- **P4 意图栈不做**（评估文档理由：有状态架构、跨客户端串意图——复核后仍成立，且 `types.ts` 已明确不引入 Redis 会话）。
- **但「识别 Agent 客户」不需要内容状态**，因为 **Chat Completions 的请求体本身携带完整对话历史**：一次请求的 `messages` 数组就是一个「会话窗口」。这让「跨 turn 特征」可以在**单请求内**计算，无需存储任何跨请求内容。这是本次对评估文档 §3.3「P4 不做」的实质性修订依据。
- 需要的跨请求状态只有两类：**计数**（`keyId + 时间桶 + 整数计数器`）与**有界哈希集合**（`keyId + payloadHash + ts`，TTL 清理）。它们不含内容、不含语义，与 P4 的 `goal/subgoals/expected_tools` 有本质区别。
- **指纹的落地动作必须限制在低风险集合**：文档推荐、控制台提示、额度/成本提醒、销售线索排序。**禁止**用指纹自动改变客户的计费、限速、内容处理方式（那会产生申诉与合规争议）。

### 5.1 可计算的指纹定义（每个特征从哪来）

| 特征 | 定义（全部可由单请求或短窗口计数得出） | 来源 |
|---|---|---|
| `hasTools` | `Array.isArray(body.tools) && body.tools.length > 0` | 单请求 |
| `hasToolCalls` | `messages` 中存在 `role='assistant' && tool_calls?.length>0`，或存在 `role='tool'` | 单请求 |
| `toolMsgRatio` | `count(role='tool') / messages.length` | 单请求 |
| `roleAlternation` | 相邻消息 `role` 变化次数 `/ (messages.length-1)` | 单请求 |
| `toolLoopDepth` | 完整 `(assistant with tool_calls → tool)` 配对数 | 单请求 |
| `prefixLen` | `messages.length`（**只记长度，不记内容**） | 单请求 |
| `prefixGrowthRatio` | 窗口内 `prefixLen` 非递减的请求占比（Agent 会话在累积历史） | 有界窗口（存整数序列） |
| `systemHashStability` | `HMAC(system 消息文本)` 在窗口内重复出现的次数占比 | 有界窗口（存哈希） |
| `retryBurst` | 窗口内同一 `payloadHash` 出现 ≥2 次的比例；以及「前一次 `outcome != success` 后 60s 内出现同一 `payloadHash`」的比例（错误后即时重发 = Agent 重试循环的强特征） | 有界窗口（存哈希+时间） |
| `streamRatio` / `jsonModeRatio` / `parallelToolCalls` / `toolChoicePresent` | 布尔/比例的窗口均值 | 有界窗口（计数器） |
| `concurrencyP50/P95` | 同 key 同时在飞请求数（进程内计数器采样） | 进程内计数 |
| `consumptionCV` | 每小时请求数的变异系数（脚本用户突发、Agent 平稳） | 时间桶计数 |
| `sdkHint` | `User-Agent` 匹配已知 Agent 框架（openai-python、langchain、dify、n8n…） | 单请求（**可伪造，只作加分项**） |

**合成**：`agentScore = Σ wᵢ·featureᵢ`（权重表版本化在 `ClientFingerprint.ruleVersion`），`kind = agent if agentScore ≥ fingerprint.agentThreshold`。全部特征可在 **O(messages) 单次遍历 + O(1) 计数查表**内算出，落进已冻结的 `ClientFingerprint.features`。

### 5.2 算不算规避了 P4 的隐私/串意图风险？

**答案：规避了「内容留存」这条红线，但没有自动规避「行为画像」这条灰线，必须靠第 6 节的机制兜住。** 逐条说明：

| 风险 | P4 意图栈 | P4-lite 指纹 | 判定 |
|---|---|---|---|
| 存会话内容 | 存 goal/subgoals（内容） | 只存长度、计数、HMAC | ✅ 风险消除 |
| 跨副本一致性 | 需要 Redis 或粘性会话 | 计数可容忍最终一致（指纹只影响运营建议，不影响正确性） | ✅ 架构风险消除 |
| 串意图（同一 key 多终端用户混在一起） | 会把 A 用户的意图喂给 B 用户 → **功能性事故** | 只会让 `agentScore` 失真（偏保守），**不产生跨用户内容泄漏** | ⚠️ 降级为精度问题 |
| 行为画像属个人信息 | 内容级更敏感 | 哈希 + 计数仍属个人信息（GDPR 下伪匿名数据仍是个人数据；PIPL 第 47 条也要求处理目的实现后删除） | ⚠️ **未消除**，需告知 + 目的限制 + 保留期 + 删除权（第 6 节） |
| 哈希被字典攻击反推 | — | system prompt 常是固定模板，裸 sha256 可枚举反查 | ⚠️ 必须用 **HMAC（密钥独立、不落库）**，禁用裸 sha256 |

**三条强制约束（写进实现）**：
1. 指纹**只用于内部分层统计与低风险动作**，绝不用于跨请求内容拼接、绝不进入成功响应的语义字段；
2. 任何哈希必须是带密钥的 HMAC（`hashSalt` 来自配置/环境，绝不落库），且带版本前缀（`v1:`）以支持轮换；
3. 若需要「会话级」归组，只能用客户端显式提供的 `X-Relay-Session-Id`，且该模式下仍不存正文。

### 5.3 反方意见汇总（第 5 节）

- **反方 1（最强）：这是「用技术解决产品问题」。** 客户注册时可以选择用途（Agent / 应用 / 脚本），直接问比推断更准、更省成本、更少合规争议。**部分采纳**：指纹的价值不在「识别得多准」，而在「对不上号的长尾客户」与「用量已达阈值但没说自己是 Agent」的升级提示。因此裁决中把指纹限定为**辅助信号**，并在注册/控制台提供显式声明且声明优先。
- **反方 2：误判会把脚本用户当 Agent 骚扰（推送 Pro）。** 缓解：推送有频次上限、可一键关闭、且推送内容不暴露推断细节；同时 `agentThreshold` 宁可偏高（偏保守）。
- **反方 3：窗口计数是状态，等于把「无状态」变成了「有状态」。** 反驳：状态性有量级差异。P4 需要**内容状态 + 跨副本一致性 + 生命周期与会话对齐**；P4-lite 只需要**有界 TTL 计数器 + 不可逆哈希**，重启即丢、不参与正确性判定。**但必须诚实**：它确实是「有状态」，所以必须在文档里写明「指纹不可用，网关仍能完全正常工作」。
- **反方 4：指纹给出的「Agent 客户」结论无法向客户解释。** 成立。因此**不对外输出指纹结论**（不进响应、不进控制台可见面板），只作为内部运营信号。

**第 5 节裁决**：P4 不做；P4-lite 做（内部辅助信号，低风险动作为限，HMAC + TTL + 不存正文 + 不作为正确性依据）；显式声明优先于推断。

## 6. 合规与信任：不落盘 prompt 内容的前提下做 P8 与指纹

### 6.1 结论先行

- **默认不存正文**：请求体、响应体、SSE 帧内容一律不落盘。落盘的只有：标识（`requestId`/`traceId`）、时间、计量（字节数、token 数，取上游 `usage`）、分类（`failure_reason`/`quick_action`/`rule_id`）、耗时、结果码、以及**带密钥的哈希**。
- **哈希必须是 HMAC-SHA256（`node:crypto.createHmac`）而非裸 SHA-256**：prompt 空间可枚举（system prompt 常是固定模板），裸哈希在库泄露时可被字典反推。
- **正文采样默认关闭**，开启需客户显式二次确认，且只采样失败请求、限长、脱敏、独立密钥加密、短保留期。
- **保留期 + 删除接口**是硬要求，不是可选项（PIPL 第 47 条、GDPR Art. 17 都要求「目的实现后删除 / 撤回同意后删除 / 提供删除请求通道」）。

### 6.2 具体方案

**A. 落盘字段白名单（默认）**

| 类别 | 落盘字段 | 说明 |
|---|---|---|
| 标识 | `requestId`, `traceId`, `keyId`, `tenantId`, `tier`, `clientKind`, `agentScore` | 不含正文 |
| 计量 | `bytesIn`, `bytesOut`, `promptTokens`, `completionTokens`, `cachedPromptTokens`, `costCny` | token 取上游 usage；缺失则记 null，不估算 |
| 分类 | `model`, `providerId`, `httpStatus`, `outcome`, `attemptCount`, `failureReason`, `quickAction`, `recoverable`, `precheck*`, `overheadUs` | 对应 `MeterRecord` |
| 哈希 | `payloadHash`, `responseHash?`, `systemPromptHash?`, `toolSchemaHash?` | 全部 HMAC，带版本前缀 |
| 关联 | `duplicateInWindow` | 仅计数 |

**B. 哈希方案**

- 算法：`HMAC-SHA256(key = hashSalt, msg = 规范化 JSON)`；规范化 = 稳定键序 + 去空白（保证同义请求得到同哈希）。
- 粒度（避免「整包哈希无法复用」）：
  - `payloadHash` = 整请求体规范化 → 用于重复检测（M5）；
  - `systemPromptHash` = system 消息文本 → 指纹特征（5.1）；
  - `toolSchemaHash` = `tools[]` 规范化 → 区分客户端类型；
  - **前缀哈希**（前 k 条消息）仅在**内存**中用于窗口去重，不落盘。
- 密钥管理：`meter.hashSalt` 来自环境变量/`0600` 文件，**绝不写入 SQLite**；轮换时用 `v2:` 前缀并存，避免「轮换后历史哈希全部失配」。
- **禁止**：跨用户的内容相似度导出、用户间比对排名、把哈希当内容用（例如「同 systemPromptHash 的用户共享缓存」——这正是 P6 被否决的原因之一）。

**C. opt-in 正文采样**

```
key.debugCapture: 'off' | 'errors-only' | 'sample' | 'full'   // 默认 off
```
- 仅 `pro`/企业层可开；开启需在控制台**显式勾选 + 二次确认**，文案必须写明「将落盘请求/响应正文」。
- 采集时：只采失败（`errors-only`）或按 `sampleRate`（默认 1%）；单条上限 8 KB（超出截断并标记）；入库前脱敏（`sk-`/`AKIA`/`Bearer`/邮箱/手机号/身份证/银行卡）；AES-256-GCM 加密（密钥独立于 DB）；保留期默认 **24h**，硬上限 7 天。
- 可在任意时刻关闭；关闭后不新增，且历史上采的样本按 6.2-E 清理。

**D. 保留期**

| 数据 | 默认保留 | 可配 | 清理方式 |
|---|---|---|---|
| 聚合指标（无个人信息） | 永久 | — | — |
| 明细（含哈希） | 30 天 | 1–180 天 | 定时 `DELETE` + 按天分区/`VACUUM` |
| trace（元数据） | 7 天 | 1–30 天 | 同上 |
| 正文采样 | 24h | ≤7 天 | 同上 + 密钥轮换使旧密文不可解 |

**E. 删除接口**

- `DELETE /admin/keys/{keyId}/data?scope=detail|samples|all` → 删除该 key 的明细/样本；返回删除条数与范围（供用户留证）。
- `DELETE /admin/traces/{traceId}` → 单条 trace 删除。
- `POST /admin/data-subject-requests` → 记录并流转数据主体请求（对应 GDPR Art. 17、PIPL 第 47/48/49 条）。
- **诚实声明**：聚合计数（不含标识、无法回溯到个人）不参与删除，依 PIPL 第 47 条「删除个人信息从技术上难以实现的，个人信息处理者应当停止除存储和采取必要的安全保护措施之外的处理」在隐私政策中明示。

**F. 透明与可验证（对应第 7 节的产品机制）**

1. **`X-Relay-Mode` 回显**：每个响应头带生效状态，例如 `X-Relay-Mode: precheck=observe;attribution=header;rules=p2-3/p3-7;overhead_us=180`。用户随时知道我们做了什么。
2. **字节级「透传证明」（nonce 方案，关键设计）**：
   - 请求带 `X-Relay-Verify-Nonce: <客户端随机数>`；
   - 非流式响应头返回 `X-Relay-Body-HMAC: HMAC(nonce, 响应体字节)`；
   - 客户端可用同一 nonce 复算 → **能验证我们没改体，但 nonce 只有客户端知道，因此不构成字典攻击面**（对比「返回裸 sha256 让用户核对」的方案：裸哈希可被枚举反推，不可取）。
   - 流式无法（需缓冲全体），仅非流式 + opt-in；文档明确说明该限制。
3. **严格透传模式（strict passthrough）**：一键关闭全部降损层，输出与上游字节等价（除 hop-by-hop 头）；开启后仍回显 `X-Relay-Mode: all=off` 作为证据。
4. **公开指标**：状态页公开 `relay.overhead.duration` p99 与各规则的误拦率——**让第三方能核对我们的承诺**，这是最便宜的信任资产。

**G. 与 OWASP / 法规的对应**

- OWASP LLM02（Sensitive Information Disclosure）的缓解措施中，与本层直接相关的三条：**输入验证**（= P2）、**最小权限访问**（= 度量只落计数、管理接口需 token）、**数据使用透明与可选择退出**（= 6.2-F 的开关与回显）。OWASP 明确提示「不要在错误消息或配置中泄漏敏感信息」——这正是我们对 `evidence` 默认关闭、对 500 上游文本脱敏的直接依据。
- OWASP LLM10（Unbounded Consumption）与 P2 的 `max_tokens`/上下文预算、以及网关自身的限速/并发上限相关。
- PIPL 第 47 条与 GDPR Art. 17 提供删除权依据；两者均要求「目的实现后删除」「撤回同意后删除」「提供便捷的请求受理通道」。

### 6.3 反方意见汇总（第 6 节）

- **反方 1：哈希也算个人信息，所以「不存正文」并不能免责。** 完全成立，本方案不声称免责——只声称**把风险从「内容级」降到「伪匿名计数级」**，并用目的限制/保留期/删除权兜住剩余风险。任何把它宣传成「合规无忧」的说法都是错误的。
- **反方 2：nonce HMAC 校验增加了响应头与计算成本，且用户不会真的去校验。** 成立。它的价值是**可验证性存在的证明**，而非日常使用功能；默认不启用，只在企业客户的合规审计场景开启。
- **反方 3：默认 30 天明细保留可能超企业客户的内部要求。** 因此保留期必须**可配到 1 天**，并且企业层支持 `retentionDays: 0`（只留内存聚合）。
- **反方 4：删除接口给了滥用面（误删/恶意删）。** 必须要求管理 token + 二次确认 + 操作审计日志（操作本身不含正文）。

**第 6 节裁决**：默认不存正文 + HMAC 化哈希 + 采样 opt-in（二次确认、脱敏、加密、短保留）+ 可配保留期 + 删除接口 + `X-Relay-Mode` 回显 + nonce 可验证模式。

## 7. 反方压力测试：降损层会不会反而增加流失

### 7.1 立场 A：一个只想要便宜 token 的散客

**他的核心诉求**：单价最低、能用、别烦我。他不关心错误翻译，也不关心指纹。

| 潜在抱怨 | 是否真实 | 量化后的风险 | 产品机制 |
|---|---|---|---|
| 「多一层延迟」 | **真实且最致命** | 降损层的 overhead 每 +1ms，在长上下文高频调用场景是可感知的 | 硬预算：`precheck.budgetUs`；`relay.overhead.ratio` 超 3% 自动降级；对外公开 p99 |
| 「你会拦我的请求」 | 真实 | 一次误拦 = 他整条脚本失败 | 默认 `observe`；A 类白名单才 `enforce`；`X-Relay-Precheck: off` 一键绕过；误拦自动降级 |
| 「你在加工我的数据」 | 真实（信任敏感） | 一次「你改了我的 prompt」的传言就够了 | 默认零注入成功响应；`X-Relay-Mode` 回显；strict passthrough 开关 |
| 「这些功能我不需要，凭什么算进价格」 | **真实且最根本** | 若因降损层涨价 → 直接流失到比价对手 | **对免费/标准层保持纯转发 + 同价**（评估文档的分层结论复核成立）；降损只在 Pro 层的订阅包里，而订阅本身是自愿的 |

**结论**：对散客，降损层**不应带来任何价格或行为变化**——他对我们的价值是「免费压测流量 + P8 样本」（评估文档 §5.4 的洞察复核成立），我们要做的是**不让他在无感知的情况下付出代价**（延迟、误拦、疑虑）。**会流失的唯一路径是「无感知的代价」**，因此所有机制都围绕「可感知 + 可关闭」设计。

### 7.2 立场 B：一个合规要求极高的企业

**他的核心诉求**：可采购性（能过法务与安全评审）、可审计、可证明「数据没被处理」。

| 潜在抱怨 | 是否真实 | 产品机制 |
|---|---|---|
| 「中转站一旦做处理，DPA 里的角色就变了」 | **真实且是最大障碍** | 默认最小化处理（只计数）；降损作为**独立可选子目的**在 DPA 中单列，客户可拒绝且不影响主服务；提供 zero-processing 模式 |
| 「哈希也是个人信息，伪匿名不等于匿名」 | 成立（GDPR recital 26 立场） | 目的限制 + 保留期 + 删除权 + 不用于任何其他目的；隐私政策明确写「我们保存不可逆的键控哈希与计数」 |
| 「服务端自动重试会重复计费/重复副作用」 | **成立且危险** | **非幂等请求默认不自动重试**：只对携带 `Idempotency-Key` 或显式 `X-Relay-Auto-Retry: 1` 的请求重试（依据 idempotency-key 草案的语义）；重试次数与结果全部进 trace 与 `attemptCount` |
| 「日志能不能不出去/不出境」 | 成立 | 本地 SQLite 单机部署 + 区域化 + 上传前脱敏；零运行时依赖本身降低了供应链审计面 |
| 「我要能证明它没动我的数据」 | 成立 | nonce-HMAC 校验 + `X-Relay-Mode` 回显 + strict passthrough + 配置快照导出 + **开源部分组件**（评估文档 §10.5 已提，本次建议提前到阶段 2 以缩短企业评审周期） |
| 「误拦会打断我的合规流程」 | 成立 | 误拦申诉通道 + 规则版本号 + 每 key 关闭 |

**结论**：对企业，降损层**不是卖点而是采购障碍**，除非它被设计成「可选、可关、可证明关」。因此 Pro 层不能捆绑降损（「订阅才降损」在散客侧是卖点，在企业侧是风险），正确形态是：**订阅提供额度与 SLA；降损作为模块化开关，默认继承客户策略（企业默认全关）**。

### 7.3 「可一键关闭 + 透明可验证」的具体产品机制（汇总）

1. **三级开关，优先级明确**：全局配置 → 租户/key（控制台 + `PATCH /admin/keys/{id}`）→ 单请求头（`X-Relay-Loss-Reduction: off` / `X-Relay-Precheck: off` / `X-Relay-Explain: 0`）。响应头回显最终生效值，避免「谁覆盖了谁」的争议。
2. **关闭 = 字节级等价**：关闭后响应字节流与上游一致（除 hop-by-hop 头）；用 nonce-HMAC 或字节数 + 上游 `request_id` 透传作为证据。
3. **每响应可解释**：`X-Relay-Mode`、`X-Relay-Rule-Version`、`X-Relay-Trace-Id`。
4. **改动即留痕**：任何状态码/响应体改动都记 `relay_modified` 到 trace；错误路径的附加字段也列入 trace（目标：成功路径永远 `false`）。
5. **误拦申诉即自愈**：`POST /v1/relay/disputes`（带 `traceId`）或「绕过后成功」自动触发规则降级（1.5 节）。
6. **公开可核对指标**：overhead p99、误拦率、`relay_error` 计数（恒为 0 是承诺）。
7. **文案纪律**：只承诺三件事（错误更可读 / 更多畸形请求被第一跳挡住 / prompt 原文不落盘），不承诺省 token。

### 7.4 反方意见汇总（第 7 节）

- **反方 1：把所有功能都做成默认关，那 Pro 层卖什么？** 卖「可观测与可诊断」：失败归因（L1/L2）、request trace、成本与缓存命中报表、误拦申诉优先、SLA。这些是**可感知的控制力**，而不是「替你改内容」。这也把评估文档的「Pro 卖降损」修正为「Pro 卖可观测与可诊断」——后者可持续，前者在客户侧是风险。
- **反方 2：透明会暴露我们的实现细节给对手。** 公开的是**结果指标**（overhead、误拦率），不是规则集与阈值；规则版本号只暴露版本，不暴露内容。
- **反方 3：可一键关闭会让大多数客户关掉，降损层白做。** 这个风险真实存在，且是**健康信号**：如果大多数人都关，说明该功能价值不成立，应该下线而不是强推。度量（P8）会告诉我们答案——这正是「先度量后优化」的意义。

**第 7 节裁决**：降损层在两种极端客户上都**可能增加流失**（散客因无感知代价、企业因采购障碍）；化解方式不是「更强的降损」，而是「更弱的默认 + 更强的透明 + 可证明的关闭」。

4. **Helicone / Portkey 的具体实现细节**（是否默认存正文、采样策略、删除接口形态）**未核实**：本文只引用了它们公开文档中明确写出的产品设计（隐私承诺、缓存、session 头），未引用其内部实现。

## 对评估文档的修订建议

1. **§8 技术架构建议（Go 网关 / Python 降损层 / PostgreSQL + ClickHouse）已被实际选型取代**：实际为 **Node.js 22 + TypeScript + 原生 node:http + 零运行时依赖 + SQLite**。建议全节重写，并明确「零依赖 + 单机 SQLite」是差异化卖点（可自托管、可审计、供应链面极小），而不是妥协。
2. **§3.4「P5 做不了」→ 修订为「原形态做不了，降级形态 request-level trace 做」**。依据：本层引入的失败必须可定位；异常 trace 是规则回归的样本源；`X-Relay-Trace-Id` + 客户端 session 键可提供运营视角的会话线（第 4 节）。
3. **§3.3「P4 不做」→ 修订为「意图栈不做；P4-lite 无状态指纹做，但只驱动低风险动作」**。关键依据：Chat Completions 的 `messages` 本身就是会话窗口，跨 turn 特征可在**单请求内**计算，不需要内容状态（第 5 节）。同时必须补充「伪匿名哈希仍属个人信息」的合规限定。
4. **§2.2 劣势 2「符号态提炼本质是服务端篡改响应」→ 细化为「改写 vs 附加」的区分**：禁止改写既有字段与语义；错误路径的附加不构成篡改；成功响应仅允许 opt-in 附加 relay 命名空间字段（v1 默认不做）。反例参考：OpenRouter 在成功响应上附加 `native_finish_reason`/`usage.cost`/`openrouter_metadata` 已被生态接受。
5. **§3.2 P2「轻量版」→ 补充为可实施规格**：A/B/C/D/E 五类规则分级、`reject` 仅限 A 类、三阶段 fail-open（上游前 4xx / 上游后透传 status / 流中 200+error 帧）、四层误拦恢复机制、以及「图片 URL 可达性检查默认关闭（SSRF）」的明确取舍（第 1 节）。
6. **§7.1「可验证：提供请求透传日志」→ 具体化为 nonce-HMAC 校验 + `X-Relay-Mode` 回显 + strict passthrough + 公开 overhead/误拦率**（第 6.2-F 节）。
7. **§9 财务模型「降损省 40% 上游」需下调并拆解**：本层（P2/P3）只减少**失败重试**，量级通常是个位数百分比；真实成本改善主要来自三处：①失败重试减少（P2/P3）；②prompt cache 命中率引导（M8）；③路由优化（P8 驱动）。**建议先跑 2–4 周 P8 基线再定 Pro 价格**，并把「省 40%」从对外话术中删除（同时满足第 1 节的文案纪律）。
8. **§5/§6 分层策略 → 补充两条**：①免费层也应记 P8 计数（不含明细），因为最脏的流量最需要样本；②Pro 不捆绑降损：订阅卖额度与 SLA，降损卖「可观测与可诊断」模块，企业默认全关（第 7 节）。
9. **新增：指标命名统一到 OTel `gen_ai.*` + 本地 `relay.*` 扩展前缀**，并在文档中给出降损层自身的验收门槛（overhead p99 < 2ms、ratio < 3%、A 类规则误拦率 = 0、`relay_error` = 0）。
10. **新增：外部先例段落**，证明「错误体附加 metadata + opt-in 详细元数据 + 客户端关联键的 request-level trace」是已经被 OpenRouter / Helicone 验证过的产品形态，不是自创风险（参考 12–17）。
11. **§11 路线图 → 顺序调整**：把 P8 度量基线提到阶段 1 的**第一位**（先有基线再谈优化，与 SKILL.md 的「先度量后优化」一致）；P2 的 `enforce` 规则毕业放到阶段 2 之后，由数据决定哪些规则可以拦。
12. **新增：对外文案纪律条款**（写入市场与文档规范）：本层不得宣传「省 token」；只允许「错误更可读、无效往返更少、prompt 原文不落盘」三类承诺（第 7.3 节第 7 条）。
